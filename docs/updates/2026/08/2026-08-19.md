## 2026-08-19（星期三）

- **修复 CUDA 版编译失败：/utf-8 被 MSBuild 原样传给 nvcc 导致 'A single input file is required'**
  - **背景**: 用户按 build_cuda.ps1 编译 CUDA 版 cpp_scheduler 时，ggml-cuda 的所有 .cu 文件均报 nvcc fatal: A single input file is required for a non-link phase when an outputfile is specified，编译终止。
  - **根因**:
    - cpp_scheduler/CMakeLists.txt 原在引入 llama.cpp 前用 add_compile_options(/utf-8 /Zc:char8_t-) 全局设置 MSVC 标志。该目录属性随 FetchContent 传播给 llama.cpp 的 CUDA 目标，MSBuild 生成器（Visual Studio 17 2022）会把目录级编译选项原样拼进 nvcc 命令行。
    - Windows 下 '/' 是路径分隔符，nvcc 把裸参数 /utf-8 当成输入文件，于是与真实 .cu 一起构成多个输入，报 'A single input file is required'。llama.cpp 自身的 /utf-8 用了 $<COMPILE_LANGUAGE:C/CXX> genex 限定，未泄漏，泄漏的正是本项目这行全局选项。
  - **修复**:
    - 删除全局 add_compile_options(/utf-8 /Zc:char8_t-)；改为只在 MSVC 分支用 target_compile_options 把 /utf-8 /Zc:char8_t- 加到本项目四个 C++ 目标（async_scheduler / scheduler_py / ai_scheduler / native_executor_bench）上。
    - 既保留本项目源码 UTF-8/char8_t 兼容性，又不再经 FetchContent 波及 llama.cpp 的 CUDA 编译。
  - **验证**:
    - `重新运行 cmake -S . -B build/cuda -G "Visual Studio 17 2022" -A x64 -DLLAMA_CUDA=ON -DGGML_CUDA=ON 配置成功；`
    - `grep 生成的 ggml-cuda.vcxproj 已无 /utf-8 编译标志（仅剩 XML 声明 encoding="utf-8"），nvcc 命令行恢复干净。`
  - **备注**:
    - 本次仅为编译期修复，CUDA 版仍需用户终端重跑 build_cuda.ps1 完成首次编译（约 10~30 分钟）。
    - 若后续 MSBuild 生成器再出同类问题，备选方案是改用 Ninja 生成器（CMake 原生 CUDA 支持，会自动把宿主编译选项包进 -Xcompiler），本机 ninja 位于 D:\c\bin\ninja.exe。

## 2026-08-19（星期三）

- **CUDA 版编译全链路修复：BUILD_TESTING 误开导致 tests 编译失败 + DLL 加载顺序导致误用旧版**
  - **背景**: 修复 nvcc /utf-8 泄漏后重跑 build_cuda.ps1，libuv 编译成功后又在集成测试目标失败；编译通过后进一步发现 scheduler_wrapper 实际加载的是 site-packages 里的旧版 CUDA DLL，而非新编译产物。
  - **根因**:
    - llama.cpp/libuv 在 FetchContent 中 include(CTest) 会把 BUILD_TESTING 缓存值置为 ON，而 CMakeLists 底部 option(BUILD_TESTING OFF) 无法覆盖已存在的缓存值，导致 add_subdirectory(tests) 被启用，编译引用已删除旧 API（createDefaultAPIClient / LLMEngineType 等）的 tests/integration_test.cpp 而失败。
    - scheduler_wrapper 将 site-packages 注册进 DLL 搜索路径；Windows AddDllDirectory 按"后添加先搜索"（LIFO）解析，而新编译产物目录（build/cuda/bin/Release）未注册或注册顺序不当，导致 pyd 依赖的 llama.dll / ggml-cuda.dll 实际加载了 site-packages 里 5月23日 的旧版。
  - **修复**:
    - CMakeLists 顶部（任何 FetchContent 之前）用 set(BUILD_TESTING OFF CACHE BOOL "Build tests" FORCE) 钉死测试关闭；注释掉底部 option(BUILD_TESTING) 与 if(BUILD_TESTING) 块。
    - scheduler_wrapper 在 import 循环内对实际选中的 pyd 目录动态注册 os.path.join(os.path.dirname(path), 'bin', 'Release')，利用 LIFO 特性（最后注册最优先）确保优先加载与所选 pyd 配套的新编译 DLL，site-packages 仅作兜底。
  - **验证**:
    - `重跑 cmake 配置 + 增量构建，退出码 0，Release 下生成 scheduler_py.pyd / async_scheduler.lib / ai_scheduler.exe；`
    - `新增 tests/scripts/cpp_scheduler/verify_cuda_backend.py 并用 venv_core 运行通过（AST 静态检查 + cuda 模式运行时反射）；`
    - `cuda/auto 模式：pyd 来自 build/cuda/Release，llama.dll 与 ggml-cuda.dll 来自 build/cuda/bin/Release；cpu 模式：来自 build/Release，不加载 ggml-cuda。`
  - **备注**:
    - 本机 CUDA v12.8 + VS2022 BuildTools，构建经 subst Z: 映射规避路径空格；产物输出到 build/cuda/Release 与 build/cuda/bin/Release，CPU 版 build/Release 保持不动。
    - 运行时切换：$env:XIAOYOU_CPP_BACKEND='cuda' 用 GPU 推理，'cpu' 用 CPU，不设置（auto）有 CUDA 版则优先 CUDA。

## 2026-08-19（周三）

- **修复 Android 端聊天图片/表情包显示为破图占位的问题**
  - **背景**: Android 聊天界面中后端下发的图片（如 AI 生图、表情包）显示为带感叹号的破图占位，用户上传的图片也无法正常显示。
  - **根因**:
    - 后端返回的图片地址是相对路径（如 /output/image/xxx），AsyncImage 默认 Coil ImageLoader 没有 host，无法解析。
    - AvelineApplication 未配置全局 Coil ImageLoader，图片请求缺少鉴权头和统一缓存策略。
    - 后端 /api/v1/upload 只返回 file_path，Android FileUploadManager 期望 file_url / url，导致上传图片 URL 为空。
  - **修复**:
    - 新增 ImageUrlResolver 工具类，将 data/http/https 之外的路径统一拼接为后端 base URL 的绝对地址。
    - 在 MessageBubble 的 MessageImage 和 ImageMessageBubble 中调用 ImageUrlResolver 解析 imageUrl。
    - 在 AvelineApplication.onCreate 中通过 Coil.setImageLoader 配置带 OkHttpClient 的全局 ImageLoader。
    - 后端 upload_file 接口在返回 data 中同时携带 file_path 与 file_url，兼容 Web 与 Android 客户端。
  - **验证**:
    - `tests/scripts/android/verify_image_url_resolution.py`
    - `clients/frontend/aveline-android/android/app/src/test/java/com/aveline/ai/mobile/utils/ImageUrlResolverTest.kt`
  - **备注**:
    - 不影响 Web 端（仍使用 file_path）。
