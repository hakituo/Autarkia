## 2026-08-22（周六）

- **统一“叫醒睡回”与“打断做事”的回原状态逻辑**
  - **背景**: 用户反馈被叫醒后聊天结束仍要等几十分钟才睡；而打断做事时又存在“明明还在聊天就回去”的情况。两套行为本质都是“交互结束→回到原状态”，但决策层不一致：叫醒走 LLM 自由决策且能拖延几十分钟，打断做事仅在校验显式回复时才顺延，平时聊天到点就回。
  - **根因**:
    - 叫醒睡回走 finalize_sleep_recovery_check 的 NIGHT_AWAKE 分支，用 LLM sleep_decision 自由选 return_to_sleep/sleep_later/stay_awake，导致聊完还被拖延几十分钟。
    - 打断做事的 _decide_work_return_should_defer 仅在 user_reply 显式存在时才顺延，平时聊天到点就回去做事，缺少“用户还在聊就顺延”的兜底。
    - chat_reply_runtime._notify_sleep_resume_message 收到的是 SleepRuntimeState（无 .get 方法），每次唤醒睡回都在此抛 AttributeError 被 except 吞掉并刷“判定失败” warning，第二条睡回消息从未真正发出。
  - **修复**:
    - reply_policy_support.py 新增共享判定 is_user_recently_active()：以 active_care 缓存的“最近用户消息时间戳”判断用户是否仍在聊（每条用户消息都会更新，信号精确）。
    - sleep_manager.finalize_sleep_recovery_check 的 NIGHT_AWAKE（被叫醒）分支改为静默窗口到达即确定性睡回，去掉 LLM 拖延；STAY_UP_LATE/SLEEP_LATER（用户主动熬夜）仍走原 LLM 决策不受影响。
    - activity_return._decide_work_return_should_defer 增加确定性前置：最近 90s 内有用户消息即直接顺延，不再依赖 LLM 误判后“还在聊就回去”。
    - chat_reply_runtime._notify_sleep_resume_message 开头兼容 SleepRuntimeState 与 dict 两种入参，修复老崩溃。
  - **验证**:
    - `tests/scripts/verify_sleep_return_unification.py`
  - **备注**:
    - 唤醒用静默窗口 silence_window_seconds（默认 180s），打断做事用 RECENT_ACTIVITY_GRACE_SECONDS（默认 90s），可按体感调节。
    - 睡回消息现会发两条（_on_enter_sleeping 的“我又去睡了” + _notify_sleep_resume_message 的“我先继续睡会儿啦”）；如需合并为一条可再调整。
