  - **背景**: 用户反馈：'AI 第一次写时自动建' 这个设计不合理——AI 主要职责是查看和抽查，记录是用户自己做的，不应该让 AI 的写入操作来触发文件创建。应该后端启动时就建好今天的空文件，用户直接往里写单词即可。同时用户问'可以看前几天背的吗'，确认需要支持看历史日期（原实现已支持，默认 7 天）。
  - **根因**:
    - 原 daily_word_log.py 用 lazy 创建策略，mark_unknown 新词追加时才 ensure_today_file，与'AI 主要读取、用户主要写入'的职责划分矛盾
    - 未在 lifespan 启动序列里调用 ensure_today_file
  - **修复**:
    - core/lifecycle/lifespan.py 在月度总结补跑检查之后新增调用 get_daily_word_log().ensure_today_file()，后端启动时自动创建今天的空文件（幂等，已存在不覆盖）
    - core/tools/study/english/daily_word_log.py 的 ensure_today_file 方法注释改为'后端启动时调用'，mark_unknown 新词追加路径保留 ensure_today_file 作为跨天后后端未重启的兜底
    - core/services/study/persona/study_persona_profile.py 提示词补充：每日日志默认看最近 7 天，AI 可用 date 参数指定某一天、用 days 扩大范围；明确'后端启动时已预创建今天的空文件'，AI 主要职责是读取和抽查
  - **验证**:
    - `tests/scripts/study/verify_daily_word_log.py 17 项测试全过（无回归）`
    - `ruff 检查 0 错误`
  - **备注**:
    - AI 看前几天背的：默认看最近 7 天（days=7），可指定 days=14 看两周，或用 date='2026/08/03' 指定某一天
    - 用户记录方式：直接在 data/study_data/English/Words/daily/YYYY/MM/DD.txt 里写单词（每行一个或 'word count'），后端启动时今天的文件已建好
    - AI 记录的单词（测验时用户说不认识）会自动 +1 写回对应日期文件，写回策略是'最近一次出现该词的那天'

- **学习生活计划生成失败兜底与今日计划工具**
  - **背景**: 用户反馈 Aveline 说今天的计划表是空的，但 active care priority 也因此只有画像兜底一条候选。排查发现 plan.json 的 items=[]，source=ai_generated，说明 LLM 调用走的是成功分支但 items 为空，notes 被 None 覆盖无法诊断。
  - **根因**:
    - generate_tomorrow_plan 成功分支直接用 LLM 返回的 notes（str(data.get('notes') or '').strip() or None），items 为空时 notes 也为空被 None 覆盖
    - LLM 返回空 items 时仍走成功分支保存 plan.json，导致下次夜间任务因 existing 跳过
    - 没有 generate_today_plan 工具，AI 无法为今天主动生成计划，只能一条条 add_plan_item
  - **修复**:
    - 抽出 _generate_plan_for_date 复用核心逻辑，generate_tomorrow_plan / generate_today_plan 都调它
    - 新增 _call_llm_and_build_plan：空返回/解析失败/非 dict/空 items 时返回 None，并记录 raw_out 前 200 字便于诊断
    - _generate_plan_for_date 首次返回 None 时重试 1 次，仍失败返回带诊断 notes 的空计划且不保存 plan.json（下次夜间任务可自动重试）
    - 新增 GenerateTodayPlanTool 工具并注册到 registry，AI 可在用户问起时为今天生成计划

- **安卓端性能与稳定性优化(7项)**
  - **背景**: 扫描 aveline-android 安卓端代码,针对内存/主线程/协程/Compose/生命周期/数据库/崩溃风险等维度,识别出 7 个「改了就有明显收益」的优化点并逐一修复,编译通过。
  - **根因**:
    - AppPreferences 的 backendUrl/userId/userName/accessToken/currentSessionId 5 个 setter 用 .commit() 同步落盘,accessToken 还含加密开销,且被 ChatViewModel.switchSession 在主线程调用,导致切会话时主线程卡顿
    - ChatRepositoryImpl.loadHistoryFromApi 用 forEach 逐条 insertMessage,DAO 无批量接口,200 条历史=200 个独立事务,IO 放大严重
    - TTSEngine 是 @Singleton 但 clearCache 仅被 destroy 调用,而 destroy 永不触发,TTS 缓存目录 tts_*.wav 无限增长
    - TTSEngine 的 scope = CoroutineScope(Dispatchers.Main) 缺 SupervisorJob,单次异常会取消整个 scope 导致 TTS 永久失效
    - WebSocketManager.onOpen 在重连场景(reconnectAttempts>0)只 sendReconnect 不启动心跳,若后端只回 reconnect_sync 不重发 connection_established,心跳永不恢复,连接静默断开后无法探活

    - TTSEngine:新增 trimCacheIfNeeded(cacheDir, incomingBytes),写入前按 lastModified 最旧优先淘汰,上限 50MB,避免缓存目录无限膨胀
