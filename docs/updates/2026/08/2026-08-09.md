    - 清理 8-09 限额文件中 Aveline 自身旧数据

    - 手机端会话限额双重判断上线后需在真机验证（依赖 Shizuku 强退）

## 2026-08-09（周日）

- **修复 Android 端 WebSocket 反复 403（buildWsUrl 协议头转换 bug）**
  - **背景**: Android 端 WebSocket 连接反复 403 Forbidden，日志显示 path 为 //192.0.2.1:8000/api/v1/ws（正常应为 /api/v1/ws），整个 host:port 段被当成 path 落入后端静态文件挂载点被拒。
  - **根因**:
    - WebSocketManager.buildWsUrl 用 Kotlin String.replaceFirst("^http", "ws") 做协议头转换，但该重载是字面量匹配而非正则，"^http" 只匹配字面 5 个字符，不会匹配以 http 开头的字符串
    - 由于 validateBackendUrl 强制要求 backendUrl 以 http:// 或 https:// 开头，用户存入的地址一定带 http(s):// 前缀，replaceFirst 不匹配后 wsBase 仍为 http://host
    - 兜底逻辑把未以 ws(s):// 开头的字符串拼成 wss://http://host，OkHttp 解析后 host 段被当成 "http"，真正的 //host:port/api/v1/ws 全部落入 path
    - NetworkModule 的 baseUrlInterceptor 只修正 scheme/host/port 不修正 path，最终服务端收到畸形 path 匹配不到 /api/v1/ws 路由，落入 HTTPOnlyStaticFiles 挂载点被拒（403）
  - **修复**:
    - WebSocketManager: 提取 normalizeWsScheme 到 companion object，用 startsWith 显式分支替代有歧义的 replaceFirst，正确把 http:// 转 ws://、https:// 转 wss://、无协议头补 wss://
    - CompanionModelTab.kt: 顺带补上缺失的 Box 与 TextOverflow import（预先存在的编译错误，阻止测试运行）
  - **验证**:
    - `tests/scripts/android_ws_url/verify_ws_url_scheme_fix.py（Python 等价实现，对比新旧逻辑，9 用例全部通过）`
    - `app/src/test/java/com/aveline/ai/mobile/data/remote/api/WebSocketManagerUrlTest.kt（Kotlin 单元测试，因其他测试预先编译错误未能运行，逻辑由 Python 脚本等价覆盖）`
  - **备注**:
    - Kotlin String.replaceFirst 有两个重载：replaceFirst(oldValue: String, newValue: String) 字面量匹配，replaceFirst(regex: Regex, replacement: String) 正则匹配；带 ^ 锚点时必须用 Regex 版本或改用 startsWith
    - 旧的 replaceFirst 注释里已写了 '协议相对写法 //host:port 必须先 removePrefix(//)' 的兜底，但因为 replaceFirst 本身就失效，http:// 的场景从未被正确处理

## 2026-08-09（周六）

- **数字健康：QQ 免限额 + 超限改为每周期持续强退**
  - **背景**: 用户明确要求 QQ 不设时长限额；同时反馈超限后仍能重新打开应用继续使用，原因是手机端强退为'当天每应用只拦一次'的周期性强退，且依赖 WorkManager 15 分钟最小周期。
  - **根因**:
    - QQ 被 nightly 规则兜底自动设了每日限额，用户不认可聊天工具被限额
    - UsageLimitMonitor 用 stoppedSet 记录'当天已强退'并跳过后续检查，导致超限应用强退一次后全天不再拦截
    - WorkManager 的 PeriodicWork 最小周期为 15 分钟，无法做到实时封锁
  - **修复**:
    - 服务层新增 _USER_NO_LIMIT_PREFIXES 排除列表，QQ 不再被 nightly 自动设限，也不参与超限强退
    - 清理 8-09 限额文件中的 QQ 条目，仅保留哔哩哔哩
    - UsageLimitMonitor 去掉'当天每应用只拦一次'的 stoppedSet 逻辑，改为每周期只要超限就强退 + 本地通知，形成持续打断
    - 保持 15 分钟检查周期（WorkManager 最小周期）
  - **验证**:
    - `8-09 限额文件仅剩哔哩哔哩一条`
    - `手机端 UsageLimitMonitor 已改为每周期无条件强退超限应用`
  - **备注**:
    - 每周期强退仍非实时封锁：用户每次被打断后最多还能用到下一个 15 分钟周期
    - 强退依赖 Shizuku 常驻，未授权时强退会静默失败

- **修复 Active Care 主动消息无法送达 QQ（conversation_id 路由失效）**
  - **背景**: 用户反馈连着 QQ 但今天没收到任何 active care 主动关怀。后端日志显示 active care 多次触发并调用 dispatch_proactive_message 且显示「已实时送达」，但 QQ 端 0 条消息，QQ 适配器日志今天无 proactive_message 处理记录。
  - **根因**:
    - build_persona_conversation_id(clients/bots/qq/utils.py)为跨平台记忆互通改用 'shared' 作 base，persona conversation_id 从 private_xxx__persona__xxx 变为 shared__persona__xxx；但 QQ 适配器 receiver.py 的 persona 匹配分支仍用 base_cid == session.session_id（private_xxx）判断，shared base 永不匹配，带 persona 后缀的 proactive_message 全被忽略
    - active care 主流程 checker_action_flow 传 client_type=ctx.client_type，而 probe_client_type() 优先返回非QQ(websocket)，当 mobile_user 在线时 client_type 非 qq，conversation_router 跳过 QQ persona 路由，target 退化为纯 private_xxx
    - proactive_messaging.py 的 dispatch_proactive_message 使用 broadcast_user_id 变量但函数内从未定义，运行的是旧代码（后端未重启）

  - **修复**:
    - receiver.py: 放宽 persona 匹配，base_cid == session.session_id or base_cid == 'shared' 都进入 persona 校验
    - client_utils.py: probe_client_type 改为优先返回 QQ（主动推送主渠道），QQ 在线时返回 qq 而非 websocket
    - proactive_messaging.py: 定义 broadcast_user_id = original_primary_conversation_id or target_conversation_id
    - peer_script_dispatch.py: 传入 original_primary_conversation_id=base_cid，确保 peer_chat 广播到主人连接
  - **验证**:
