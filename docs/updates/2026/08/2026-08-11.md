## 2026-08-11（星期二）

- **修复数字健康页面「今天一片空白」**
  - **现象**: 改为拉"今天"限额后, 今天打开数字健康页面完全为空, 一个应用都没有。
  - **根因**: 后端 `GET /wellbeing/app-limits` 不传 `target_date` 时默认拉**明天**的限额文件 (`limits_{明日}.json`); 而前端昨天改成拉**今天**。今天(及任意当天)的限额文件本来就没被任何流程写入 (nightly 的 `build_limit_suggestion` 从未被接通、用户当天也没手动设过), 于是返回空列表 → 空白页面。
  - **修复** (`routers/v1/context_device.py:get_app_limits`):
    - 默认 `target_date` 改为**今天** (与前端对齐, 数字健康核心诉求是看今日真实用量)
    - 增加**回退逻辑**: 当天无限额记录但有今日用量 (`read_today_app_usage`) 时, 把有今日用量的应用也返回 ( `limit_ms=0` 表示"未设限额"), 保证页面永远展示今日真实使用情况
    - 返回补充 `session_cap_ms` 字段 (前端 `AppLimitDto` 已支持)
  - **注意**: 若今天还没发生过同步 ( `app_usage.jsonl` 今天文件不存在), 回退也取不到用量, 仍会空。这是预期行为——先让手机同步一次即可。

- **修复数字健康「计时不准」+「没在用却触发 active care」**
  - **背景**: 用户反馈每天打开数字健康页面，哔哩哔哩都是固定显示 3h40m，且明明没在用却触发超额关怀。
  - **根因一 (3h40m 固化)**: `DataSyncWorker.getAppUsage(hours=24)` 查询过去 24h 的 UsageStatsManager `INTERVAL_DAILY` bucket，会混入昨天的全天用量。后端 `read_today_app_usage` 再取历史最大值聚合，某天峰值 3h40m 被永久保留。
  - **根因二 (假关怀)**: `maybe_notify_exceeded_via_active_care` 只判断"今日累计用量超限"，不问"用户此刻是否在活跃"，当 24h 窗口把昨天数据带进来 + 后端一直看到 3h40m 超限，每条同步都触发 active care。
  - **根因三 (日期/聚合口径不一致)**: `WellbeingViewModel.refresh()` 拉今天、后端默认返回明天限额；`read_today_app_usage` 用最大值而非最新值聚合；`UsageLimitMonitor` 同样用 24h 窗口做本地强退判断。
  - **修复**:
    - `DataSyncWorker.kt`: `getAppUsage(hours=24)` → `getAppUsageSince(todayMidnightMs)`，只上报今天 00:00 至今的用量，切断昨天数据污染源头
    - `UsageLimitMonitor.kt`: 同上 + 会话 cap 从"全局最早起点"改为"每个应用按各自生效起点独立查询"，修复后设应用的用量被错误计入
    - `routers/v1/context_device.py:read_today_app_usage`: 聚合从"取 usage_time_ms 最大值"改为"取 server_timestamp 最新的一条"，防御旧版安卓仍可能混入历史数据
    - `core/services/digital_wellbeing/service.py:maybe_notify_exceeded_via_active_care`: 增加 `last_used_time` 最近活跃检查 (默认 30min)，应用最后使用时间超过窗口则跳过关怀
    - `AppLimitDto.kt`: 新增 `sessionCapMs` 字段，`WellbeingScreen` 卡片展示一次性会话限额
    - `WellbeingViewModel.kt`: 修正日期注释和 date 字段无操作 bug
    - `WellbeingScreen.kt`: `formatDuration` 边界修复 (ms<60s 显示 `<1m` 而非 `0s`)
  - **验证**: Android 重新上报只含今天的数据 → 后端聚合取最新时间戳 → 前端进度条反映真实今日用量。active care 仅在应用最近 30 分钟内被使用过时才触发。

- **修复安卓聊天界面「Mian」和「Frost」头像变成同一张**
  - **背景**: 用户反馈安卓端给不同角色设置自定义头像后，Mian和Frost的头像会互相变成一样。
  - **修复**:
    - `PersonaAvatarStorage.sanitize()`：在可读前缀后追加原始 filename 的 MD5 前 12 位哈希，保证不同 persona 文件名唯一，同时压缩连续下划线并限长
    - `PersonaLocalMetaRepository.repairDuplicatedAvatars()`：新增一次性脏数据修复，检测多个 persona 共用同一 `avatarPath` 的记录，删除冲突物理文件并把 `avatarPath` 置空（回退后端默认/首字兜底）
    - `AvelineApplication.onCreate()`：启动时在 IO 协程调用上述修复
  - **验证**: 覆盖安装后启动 App，确认Mian/Frost头像回退为默认，重新分别设置头像后两者互不影响。

- **修复 Active Care 后端已存储今日餐饮仍追问"早餐吃了没"**
  - **背景**: 用户已通过 `/吃` 等指令把"今天早餐吃什么"写入后端 daily_record 的 meals，但 Active Care 仍主动问"早餐吃了没？"。
  - **根因**: `detect_user_already_covered` (core/services/active_care/decision/portrait_keyword_map.py) 仅匹配用户聊天文字里的吃饭关键词，未查询后端 daily_record 已存的今日餐饮。
  - **修复**: 在该函数合并 `_detect_backend_meals_covered()`：查询 `get_daily_manager().get_record()["meals"]`，若含"早餐/午餐/晚餐"正餐记录则把 "meal" 计入已覆盖集合，触发 `meal` 硬约束与画像过滤，不再追问。
  - **验证**: 记录今日正餐后触发 Active Care，确认主动消息不再出现"吃了没/早餐吃了没"。

- **修复 module 日志丢失 / peer_chat role_ids 未定义 / 澄清 QQ 注册表 0 实例**
  - **背景**: 排查 08-10 早上 active_care_schedule.log 等 9 个 module 日志在 05:21 集体停止写入，而主日志 xiaoyou_main.log 继续。
  - **根因**:
    - 所有日志走同一 QueueListener；module 日志 handler 由 get_module_logger 动态 append 到 _queue_listener.handlers
    - _restart_queue_listener 重启时调用 _setup_handlers，只重建 main handler，module fh 全部丢失；且 _module_file_handlers 缓存命中导致 get_module_logger 不再重新 append，module 日志永久丢失直到进程重启
    - peer_chat_scheduler.is_user_sleeping 使用了未定义的 role_ids 变量，抛出 NameError
  - **修复**:
    - core/utils/logger.py _setup_handlers：创建 QueueListener 时用 globals().get('_module_file_handlers') 收集所有 module fh 一并挂载，QueueListener 重启后 module 日志不再丢失
    - core/services/active_care/peer_chat/peer_chat_scheduler.py is_user_sleeping：改为从 _get_multi_qq_connections() 获取可参与互聊角色列表，修复 role_ids 未定义
  - **验证**:
    - `重启后端后观察 active_care_schedule.log 等 module 日志持续写入`
    - `peer_chat_scheduler 不再出现 'is_user_sleeping 检查异常'`
