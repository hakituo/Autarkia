## 2026-10-14（周三）

- **主动关怀接入专用决策模型引擎（影子模式）**
  - **背景**: 主动关怀的决策槽位一直由 MiniMax-M3 承担，实测单次成本约 0.02 元、延迟 15 秒（一天 36 次 priority 调用有 18 次真超时），且账单里输出 token 占七成成本。2026 年 9-10 月出现了专门的「结构化决策模型」品类（Jev、Microsoft-Decision-1、OpenAI Luna Decisions 等），按输入计费、输出免费，单次成本低一到两个数量级。需要在不动线上发送行为的前提下先并行观察它们与现有决策的一致率。
  - **根因**:
    - 决策槽位用的是通用生成模型，输出按 8.4 元/百万计费且因 MiniMax 客户端 pop 掉 max_tokens 而没有上限。
    - 决策协议自 2026-09-04 起已收敛为「只回答 send / defer + retry_after_seconds」，本来就是纯分类任务，却没有用专用决策模型。
    - 现有决策 prompt 是约 9k 字符的完整上下文 dump，噪声淹没信号，且决策模型只按输入计费、state 越长越贵。
  - **修复**:
    - 新增 core/llm/decisions 子包：OpenRouter /api/alpha/decisions 客户端，一个客户端同时支持 Luna Decisions 与 Microsoft-Decision-1（两者共用同一套 {state, questions} 协议）。
    - 新增 core/services/active_care/decision/engine 子包：compact_state 把决策上下文压成事实清单（实测 9k 字符降到约 200 字符），shadow 并行跑决策模型只记日志不切换。
    - content_planner 决策链路挂 maybe_run_decision_shadow 钩子；影子链路自带超时与异常兜底，永不抛出、永不改变发送行为。
    - 影子模式在 pytest 进程中无条件跳过，避免测试驱动决策链路时发起真实网络请求。
    - 新增三个配置项：active_care_decision_shadow_enabled / _models / active_care_decision_send_threshold。
  - **验证**:
    - `venv_cpu\Scripts\python.exe -m pytest tests/unit/test_active_care_decision_engine.py -q`
    - `venv_cpu\Scripts\python.exe tests\scripts\active_care\verify_decision_model_engine.py`
    - `venv_cpu\Scripts\python.exe tests\scripts\active_care\verify_decision_model_engine.py --live`
  - **备注**:
    - Microsoft-Decision-1 不在 OpenRouter 公开模型目录里，但确实挂在 /api/alpha/decisions 上；用 chat/completions 调它会返回 400 并提示改用该端点。
    - 实测同一段 state：MiniMax-M3 约 0.0078 元、Luna 约 0.0033 元、Microsoft-Decision-1 约 0.0011 元。
    - 精编 state 不只是省钱手段：拿完整上下文 dump 时模型会对「用户要求的提醒已到期」答 0.00，压成事实清单后答 1.00。

## 2026-10-14（周三）

- **主动关怀投递渠道策略（QQ / App 分流）**
  - **背景**: 主动关怀此前固定「QQ 主投 + App 在线即无条件补投」，用户同时挂着 QQ 和 App 时同一条消息会在两端各弹一次。需要把「发哪一端」从硬编码改成可配置、可审计的策略，并保留退回到旧行为的开关。
  - **根因**:
    - probe_client_type 只要有 QQ 连接就返回 qq，QQ 被写死为主渠道，App 补投没有判断依据。
    - 投递端缺少统一决策点，补投逻辑与主广播耦合在同一个函数里。
  - **修复**:
    - 新增 core/services/active_care/core/channel_policy.py：纯函数 decide_channel 按模式与场景返回两端投递开关 + 命中规则名。
    - 新增配置 active_care_channel_mode，取值 mirror_app（默认，等于改动前）/ prefer_app / prefer_qq / smart；非法值回退 mirror_app。
    - proactive_messaging.dispatch_proactive_message 改为先决策再投递；App 优先模式下 App 投递失败会自动回退 QQ 主投，不存在两端都不发的组合。
    - message_dispatcher 把 sys_prompt_type 带进 extra_payload，供渠道策略按消息类型分流。
  - **验证**:
    - `venv_cpu\Scripts\python.exe -m pytest tests/unit/test_active_care_channel_policy.py -q`
    - `venv_cpu\Scripts\python.exe -m pytest tests/unit/test_active_care_app_delivery.py -q`
    - `venv_cpu\Scripts\python.exe tests\scripts\active_care\verify_active_care_channel_policy.py --report 2026-10-13`
  - **备注**:
    - app.yaml 里 active_care_channel_mode 保持 mirror_app 不动，等人工看过决策矩阵再决定是否切 smart。
    - smart 的规则是：作息/健康类两端都发，App 离线只发 QQ，用户在 QQ 只发 QQ，用户在 App 只发 App，判不出触发端就双投。

## 2026-10-14（星期三）

- **修复电脑截图只截到屏幕一角（4K + 150% 缩放下 DPI 坐标系错位）**
  - **背景**: 用户反馈 companion_data/temp/screen_captures/ 里的截图只有左上角一小块有内容、其余全黑（旧图 1920x1080 里仅左上角 640x976 有效）。用户为 4K 屏（物理 3840x2160、系统缩放 150%），此前一直以为「只截了一小部分」是窗口选择问题。
  - **根因**:
    - 截图线程是 DPI-unaware：Win32 的 GetSystemMetrics / GetMonitorInfoW 返回被系统按缩放比虚拟化后的逻辑坐标（4K@150% 只报 2560x1440），而 Pillow 的 ImageGrab 抓出来的是物理像素位图 3840x2160，两个坐标系不一致。
    - 拿 2560x1440 的 bbox 去裁剪 3840x2160 的位图，实际只覆盖屏幕左上角 (2560/3840)x(1440/2160) ≈ 67%x67%，越界部分被 PIL 用黑色补齐 —— 这就是「只有一小部分」的来源。
    - 多屏下更严重：ImageGrab.grab(bbox=...) 只抓主屏位图、却按绝对坐标裁剪，副屏区域会整片全黑（2026-10-02 日志里 bbox=(1707,-139,4267,1301) 即此情形，截出来几乎全黑）。
  - **修复**:
    - 新增 core/tools/screen_capture/win_screen.py：把 Win32 屏幕几何与抓屏原语独立成一层，用 per_monitor_dpi_aware() 上下文管理器在同一线程内临时切到 per-monitor DPI aware，退出时还原，保证「算坐标」和「抓位图」永远落在同一（物理像素）坐标系。
    - 抓图统一走「整块虚拟桌面位图 + 手动裁剪，并把裁剪框夹取到屏幕范围内」，不再依赖 ImageGrab.grab(bbox=...)，从根上消除多屏错位与黑色补齐。
    - 截图目标由「整块显示器」改为「鼠标所在窗口 → 前台窗口 → 其所在显示器 → 整屏」优先级；窗口已最大化（≥92% 显示器面积）或小于 64px 时按整屏截，避免漏掉任务栏与边缘。
    - core/tools/screen_capture_tool.py 收敛为薄壳门面（351 → 329 行），Win32 相关代码全部外移，业务策略（截哪块、压缩分档、清理）留在原处。
  - **验证**:
    - `tests/scripts/tools/verify_screen_capture_tool.py 10/10 通过；实测截图 1815x1375 内容铺满整帧、纯黑占比 0%（修复前同目录截图只有左上角有内容）。`
    - `活动屏幕边界由虚拟化坐标 (0,0,2560,1440) 变为物理坐标 (0,0,3840,2160)。`
    - `CI 同款全量 pytest：10 failed / 5800 passed，失败集合与改动前完全一致（test_cross_platform_paths 7 + test_active_care_activity_context 2 + test_activity_instance_runtime 1），无新增失败。`
    - `tests/scripts/docs/check_file_sizes.py 无新增超限；tests/scripts/docs/check_rules_consistency.py 通过；ruff 无告警。`
  - **备注**:
    - 验证脚本测试 8 原先真读系统空闲时间，无人操作时会误判成挂机而失败，已 mock 掉挂机检测（挂机分支本身由测试 4 覆盖），脚本不再依赖操作者是否在电脑前。
