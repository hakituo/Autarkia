## 2026-10-28（星期三）

- **安卓 ASR 点「录音完成」偶发闪退：native 并发与 AudioRecord 泄漏**
  - **背景**: 用户反馈安卓 App 用 ASR 时点「录音完成」有很小概率直接闪退（约一天一次），崩溃日志目录里什么都没有，无法从 CrashHandler 拿到栈。
  - **根因**:
    - SherpaNcnn 的 acceptSamples / decode / inputFinished / reset 在 C++ 侧共用同一套解码状态和裸指针，但引擎里没有任何互斥：录音循环（IO）、收尾解码（IO）、取消后的清理 reset（IO）、开录时的 reset（主线程）都可能同时进 native。这类崩溃是 SIGSEGV，CrashHandler 只抓 Java 异常，所以日志目录是空的。
    - 开录前判断「上一轮收尾解码是否结束」用的是 Job.isActive：Job 一旦被 cancel，isActive 立刻变 false，但 native decode 可能还在跑。于是「取消 → 立刻再录」会直接撞进同一段 native。
    - cancel() 只等收尾解码、不等录音循环，随后就 recognizer.reset()；而 AudioRecord.read 是阻塞调用，协程 cancel 打断不了它，旧循环还活着时 reset / acceptSamples 就并发进 native。
    - 录音循环里 read 返回 0 或错误码时无条件写 state=Error，会把 stopListening 刚设的 Processing 覆盖掉，收尾解码随即放弃（表现为点了完成、最终结果没替换）。
    - AudioRecord 每次开录 new 一支，但只 stop 不 release（全仓唯一的 release 在 destroy 里，而 destroy 从没被调用过），一路漏到 AudioFlinger 的录音客户端。
  - **修复**:
    - SherpaNcnnAsrEngine 新增 nativeLock：录音循环、收尾解码、取消后的 reset 三处 native 调用全部串行；主线程不再放任何 native 调用。
    - 新增会话代号 sessionId，开录 / 停止 / 取消各 +1；过期会话的协程在碰 native 和写 UI 状态之前直接收手。
    - 开录互斥改用 Job.isCompleted，并在上一轮录音循环未退出时等它结束再开录（带超时、最多重试一次），不再抢同一支 AudioRecord。
    - 收尾解码先等录音循环真正退出（上限 2s）再 inputFinished / decode；等不回来就丢这一轮结果，绝不并发进 native。
    - AudioRecord 生命周期收敛：createAudioRecord 初始化失败就地 release，录音循环 finally 里只释放自己那一支；stop / release 用 recordLock 串行，read 不进锁（否则 stop 永远等不到锁，会死锁）。
    - 录音循环 read 返回 0 / 错误码时先看会话是否还活着，不再覆盖 Processing。
    - 每轮开录在第一次 acceptSamples 之前先 recognizer.reset()（同样在 nativeLock 下、在录音协程里）：上一轮收尾调过 inputFinished，不复位会带着那份状态继续解码，第二轮识别不出字。
    - SherpaNcnn 构造后校验 native 指针非 0，把握手失败导致的空指针解引用（SIGSEGV）变成可捕获的 Java 异常；initialize() 的兜底从 Exception 放宽到 Throwable。
  - **验证**:
    - `venv_cpu/bin/python tests/scripts/android_frontend/verify_asr_native_safety.py（新增）：11/11 通过，覆盖 nativeLock 串行、会话代号、isCompleted 互斥、收尾解码等待录音循环退出、AudioRecord 创建/释放闭环、recordLock、native 指针校验`
    - `venv_cpu/bin/python tests/scripts/android_frontend/verify_asr_streaming.py：22/22 通过`
