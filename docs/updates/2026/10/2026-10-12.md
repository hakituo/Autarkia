## 2026-10-12（星期一）

- **修复 LazyAsyncLock 跨事件循环复用导致用户级睡眠状态保存失败**
  - **背景**: errors_20261012.json 记录 SLEEP_STATE 在 _save_state 保存用户级睡眠状态时报 <asyncio.locks.Lock [unlocked, waiters:1]> is bound to a different event loop，睡眠事实写盘失败（异常被捕获后仅返回 False）。
  - **根因**:
    - LazyAsyncLock 首次 acquire 时创建的底层 asyncio.Lock 会被 Python 3.10 的 _LoopBoundMixin 绑定到当时运行的事件循环（且只在竞争分支校验），而锁实例被 ActiveCareStorage 等长生命周期单例长期持有。
    - 进程内事件循环重建（服务重启 / 多次 asyncio.run）后，旧循环里发生过竞争且等待队列残留未取消 Future（生产报错形态正是 unlocked+waiters:1），新循环 acquire 命中跨循环校验直接抛 RuntimeError。
    - async_locks.py 模块文档「Python 3.10+ Lock 不再绑定循环」的表述过时：3.10 只是改成首次使用时懒绑定，跨循环复用同一个锁仍会报错。
  - **修复**:
    - LazyAsyncLock.acquire 记录底层锁绑定的事件循环，发现运行循环切换时透明重建底层锁；旧锁仍处于 locked（旧循环异常关闭导致锁泄漏）时重建并 warning，暴露未正常释放的异常路径。
    - 全仓十余处 LazyAsyncLock 使用点（active_care storage、chat_agent、voice 引擎、websocket、llm client 等）随单点修复一同免疫，无需逐处改动。
    - 更新模块文档说明真实绑定语义；单测同步改造：同循环复用不重建、跨循环透明重建、旧锁泄漏重建并告警，删除对已移除 _get_lock 的引用。
  - **验证**:
    - `venv_cpu\Scripts\python.exe -m pytest tests/unit/test_concurrency_async_primitives.py -q -n 0（连跑 3 次，25 passed）`
    - `venv_cpu\Scripts\python.exe tests\scripts\monitoring\verify_20261012_lock_cross_loop.py（3/3 契约通过，连跑 3 次；含按生产形态复现旧报错的 stale waiter 场景）`
    - `CI 同款全量 pytest（7 ignore + 2 deselect）：5673 passed / 18 skipped，11 failed 均为本机环境/数据依赖存量失败，已更新 CODING_GUIDE 3.7.3 基线清单`
    - `ruff check 改动文件全过；check_file_sizes 无新增超限；audit_tests 退出码 0`
  - **备注**:
    - 修复点在通用并发基础设施而非睡眠业务层：SleepStateManager 的报错只是最先暴露的调用面。
    - errors_20261012.json 已在修复确认后删除。

- **新增日记翻旧机制（写/看日记概率性翻旧 + streak 跨天状态）**
  - **背景**: 角色写完日记后只是把当天记下来，缺少『睡前翻以前的日记』这类带心境的回顾行为。用户要求按写日记的时刻触发概率性翻旧：太晚=焦虑失眠翻旧日记，太早=没事翻了翻，并要一个偶然翻到；翻到多久之前、以及连着好几晚都在翻，都要有明确概率与状态定义。用户明确不要引算法，用显式权重表。
  - **根因**:
    - 此前翻旧行为完全依赖 LLM 自觉调用 read_diary，无概率、无时段语义、无跨天状态
    - 写日记的写入路径分散（write_entry / nightly daily_summary / auto_heal），缺少统一行为挂点
  - **修复**:
    - 新增 core/services/journal/diary_reread/ 子包：policy（时段分桶/概率/深度抽样/文案）、state_store（companion_data/{scope}_data/diary_reread_state.json 原子写）、service（编排+单例，依赖全注入）
