## 2026-04-16
- **修复 LLM 报错（[DEBUG_ERROR]）导致的问题**：
  - **问题表现**：
    1. Active Care 阶段：由于缺少拦截，云端 LLM 返回的 `[DEBUG_ERROR]` 被当作正常的主动关怀消息处理并推送到前端。
    2. Vision 视觉描述阶段：云端 LLM 报错 `[DEBUG_ERROR]` 被当作图片描述返回，导致前端一直卡在错误信息或超时。
  - **修复方案**：
    1. 在 `core/modules/vision/module.py` 的 `_describe_image_cloud` 方法中，增加对 `[DEBUG_ERROR]` 前缀的拦截，将其作为错误状态返回。
    2. 在 `core/services/active_care/executor.py` 的 `_generate_active_care_response` 及其调用处，增加对 `[DEBUG_ERROR]` 前缀或空内容的拦截，遇到错误时直接记录日志并中止 proactive 消息生成，避免异常内容泄露给用户。

- **修复 Active Care 将 LLM 报错（[DEBUG_ERROR]）直接发送给用户的 Bug（彻底修复）**：
  - **问题原因**：此前虽然在 `postprocessor.py` 中引入了 `is_debug_context_message` 拦截，但该函数仅检查字符串是否以 `[DEBUG_ERROR]` **开头**。当底层报错被保存到历史记录后，`prompt_builder.py` 会将其作为 `【去重约束】你上一条主动消息：[DEBUG_ERROR]...` 放入提示词中，导致 LLM 生成的回复包含了该报错文本及吐槽（如 `...这是什么鬼`），因为不以 `[DEBUG_ERROR]` 开头从而绕过了拦截机制并发送给用户。
  - **修复方案**：
    1. 修改 `core/utils/debug_markers.py` 中的 `is_debug_context_message`，将仅匹配开头改为**包含** `[DEBUG_ERROR]` 或 `[DEBUG_INTERNAL]` 即视为错误消息，确保任意位置出现都能被 `postprocessor` 拦截。
    2. 修改 `core/services/active_care/prompt_builder.py` 的 `_build_dedup_constraint`，在提取上一条助手消息作为去重锚点时，若发现其为 debug 错误消息，则直接丢弃，避免污染提示词导致 LLM 幻觉。

- **修复 Active Care 触发间隔异常（超时导致长达3小时不发消息）的 Bug**：
  - **问题原因**：当 LLM 生成 proactive 消息耗时过长导致 `perform_check` 触发 45s 超时 (`asyncio.TimeoutError`) 时，`executor.py` 中已经提前记录了 `_last_active_care_trigger_ts`。这导致后续 60s 后的重试被 `overlap_guard` (防重叠机制，默认 180s) 错误地拦截。拦截后系统认为本次调度已处理，从而进入长达 10 分钟以上的深度睡眠周期，如果循环触发超时则会导致数小时的沉默。
  - **修复方案**：
    1. 在 `executor.py` 的 `trigger_message` 中加入 `finally` 块：如果消息最终未成功 delivered（包括发生异常或被取消），则将 `_last_active_care_trigger_ts` 回滚，避免错误触发 overlap guard。
    2. 在 `proactive_checker.py` 中：仅当 `delivered` 为 True 时才设置正常的长间隔 `next_decision_ts`；如果失败（`delivered` 为 False），则将下一次检查时间缩短为 60s，给予系统快速重试的机会。
