## 2026-07-09（周四）

- **清理 MemoryWatchdog 屎山 + 修复 UIE 无谓加载 paddle 库**
  - **背景**: 用户反馈程序内存占用过高（PID 24084 `python main.py` 跑 14 小时 RSS 8.5GB），想用 memory watcher 诊断。检查发现：1) config/yaml/app.yaml 中 memory_watchdog.enabled=false，看门狗根本没启动；2) core/utils/memory_watchdog.py 文件里同时存在两个 MemoryWatchdog 类（行 1-315 轻量异步版 + 行 316-1101 旧重量级版），旧版主循环每次都遍历 gc.get_objects()/gc.get_referrers()，本身就是内存大户；3) 路由 routers/admin/memory_watchdog.py 依赖旧版字段（loaded_models/object_counts/dump_top_objects）；4) core/services/data_ops/uie_extractor.py 在 ONNX 模型文件不存在时回退到 paddle 后端，但 paddle 模型文件也不存在——而 import paddle 在文件检查之前，导致 paddle 库（libpaddle.pyd 99MB + mklml.dll 80MB）被无谓加载且无法卸载。
  - **根因**:
    - memory_watchdog.py 同一文件里两个 MemoryWatchdog 类共存，旧版主循环每 5 次检查会多次遍历 gc.get_objects()（_log_detailed_analysis 行 855 / _analyze_leak_source 行 683 / _analyze_objects 行 573），监控自身就是内存大户
    - routers/admin/memory_watchdog.py 的 /top-objects 调 dump_top_objects、/snapshot 和 /ws 调 _take_snapshot() 并访问 loaded_models/object_counts 字段——这些只在旧版 MemorySnapshot 里存在；/trend 还访问了不存在的 growth_history 字段
    - uie_extractor._init_paddle_backend() 在第 126 行先 `import paddle`，到第 148 行才检查 paddle 模型文件是否存在；当 ONNX 和 paddle 模型文件都不存在时，paddle 已被导入且无法卸载，~180MB DLL 常驻进程内存
    - PID 24084 实际大头是 PyTorch CUDA 库（~3.5GB DLL）+ 478 个线程栈（每线程 1-8MB）+ Python 堆对象，paddle 占 ~180MB 是次要但可避免的浪费
  - **修复**:
    - 重写 core/utils/memory_watchdog.py：删除旧版重量级 MemoryWatchdog，统一为轻量异步版；主循环 _check_memory_fast() 只用 psutil，绝不调 gc.get_objects()
    - 新增 DetailedMemorySnapshot 数据类 + take_detailed_snapshot()/analyze_top_objects()/analyze_leak_source() 按需接口，仅在 API 调用时执行 gc 遍历
    - 修复 routers/admin/memory_watchdog.py：/top-objects 改用 analyze_top_objects、/snapshot 和 /ws 改用 take_detailed_snapshot、/leak-analysis 委托给 analyze_leak_source、/trend 修正字段名 growth_history→recent_growth
    - 修复 uie_extractor._init_paddle_backend()：把 paddle 模型文件存在性检查移到 `import paddle` 之前，模型缺失时直接 raise，不再无谓加载 paddle 库
    - config/yaml/app.yaml: memory_watchdog.enabled=false→true，下次重启服务会自动启动轻量看门狗追踪长期内存趋势
  - **验证**:
    - `ruff check core/utils/memory_watchdog.py routers/admin/memory_watchdog.py → All checks passed`
    - `python -c 'from core.utils.memory_watchdog import ...; w.take_detailed_snapshot(); w.analyze_top_objects(3); w.analyze_leak_source()' → 全部接口正常`
    - `Get-Process -Id 24084 → RSS=8159.7MB, n_threads=478, 内存映射 top 20 全是 torch CUDA DLL`
  - **备注**:
    - 当前 PID 24084 已跑 14 小时无法原地深度分析 Python 堆（无法 attach tracemalloc）；启用看门狗后下次重启会自动采集基线，长期运行下能定位真正增长源
    - 478 线程的栈空间占用是 8GB 中的隐性大头之一，建议后续单独排查线程来源（可能是 torch CUDA 线程池或 dataloader workers）
    - PyTorch CUDA DLL ~3.5GB 是常驻开销，无法通过代码优化降低；若服务器部署，建议在 nvidia-smi 层面监控实际 GPU 显存使用而非进程 RSS
