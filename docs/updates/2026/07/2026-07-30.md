## 2026-07-30（周四）

- **修复紧急降级 perform_downgrade 非幂等导致 ErrorCollector LoggedError 重复上报**
  - **背景**: 免疫服务每 10s tick 检测资源，当 memory≥96% 或 cpu≥99% 触发紧急降级时，每 tick 都调用 monitor.perform_downgrade(level=3)，而 perform_downgrade 非幂等，每次都重新执行 _emergency_downgrade 并用 logger.error 记录日志。ErrorCollectorHandler 捕获所有 ERROR+ 日志作为 LoggedError 上报（带新 error_id），导致紧急状态持续期间每 10s 产生一条错误上报，并触发免疫系统自身错误暴增检测，形成噪声反馈。
  - **根因**:
    - resource_monitor.perform_downgrade 非幂等：不跟踪已应用级别，每次调用都重新执行降级动作和日志
    - _emergency_downgrade 使用 logger.error 记录降级执行，被 ErrorCollectorHandler 当作 LoggedError 上报；但降级是系统主动保护性响应，并非错误
    - immune/service._apply_resource_response 紧急/中度分支无状态转移检查，每 tick 重复调用 perform_downgrade（恢复分支有检查，但紧急/中度分支遗漏）
    - perform_downgrade(level=0) 恢复时不清除降级环境变量标记（SERVICE_DOWNGRADE_LEVEL/EMERGENCY_MODE 等），导致恢复后其他模块仍误判系统处于降级状态
  - **修复**:
    - resource_monitor.py: perform_downgrade 增加 _applied_downgrade_level 幂等控制，目标级别与已应用级别相同时跳过执行
    - resource_monitor.py: _emergency_downgrade 日志级别从 logger.error 降为 logger.warning，避免被 ErrorCollectorHandler 捕获为 LoggedError
    - resource_monitor.py: 新增 _clear_downgrade_markers，perform_downgrade(level=0) 时清除所有降级环境变量标记
    - immune/service.py: 紧急(level=3)/中度(level=2)分支增加 _last_downgrade_level 状态转移检查，与恢复分支保持一致，仅在级别变化时调用 perform_downgrade
  - **验证**:
    - `venv_core\Scripts\python tests\scripts\monitoring\verify_downgrade_idempotent_2026_07_30.py`
    - `venv_core\Scripts\python -m ruff check core/services/monitoring/resource_monitor.py core/services/immune/service.py tests/scripts/monitoring/verify_downgrade_idempotent_2026_07_30.py`
  - **备注**:
    - 验证脚本 5/5 通过：幂等性、日志级别 WARNING、环境变量清除、端到端恢复流程、immune 状态转移检查
    - ruff 检查全部通过

    - 夜间蒸馏/人物档案/角色更新统一走 cloud:deepseek:qqbot2:deepseek-v4-pro，与主对话 default key 隔离，便于 qqbot2 内跨场景共享缓存
