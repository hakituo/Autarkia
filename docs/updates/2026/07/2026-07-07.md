## 2026-07-07（周二）

- **PeerChat gate 通过后 LLM 决策阻断发送问题修复**
  - **背景**: 用户反馈 peer chat 从未互相发过一条消息。7/6 日志确认 should_trigger_peer_chat gate 通过了 5 次（概率修复已生效），但两个角色从未互相发送消息。排查发现 trigger_via_scheduler 里的 LLM 决策（decide_peer_chat）是阻断点：gate 通过后 LLM 决策返回 should_send=False 或超时(20s)降级为不发送，导致 peer chat 永远不会真正发送消息。
  - **根因**:
    - gate 已通过 5 个条件检查（时间/活动/概率/间隔/今日次数），但 trigger_via_scheduler 又调用 LLM 决策 decide_peer_chat 做重复判断
    - decide_peer_chat 有 3 个返回 should_send=False 的路径：LLM 超时(20s)、LLM 返回 False、异常
    - 决策日志用 logging.getLogger(__name__) 不写入文件，所以 7/6 日志看不到 LLM 决策结果
    - LLM 决策 prompt 规则包含'凌晨0-7点不打扰'等规则，但 gate 已做过时间检查，LLM 决策是多余的重复判断
  - **修复**:
    - 修改 engine_peer_chat_support.py 的 trigger_via_scheduler：gate 通过后 LLM 决策不再阻断发送
    - LLM 决策仍被调用，但仅用于辅助生成更好的 situation/opening_idea/topic（提升剧本质量）
    - should_send=False 时不再 return False，而是用默认 situation 继续生成剧本
    - LLM 决策异常时也不阻断，用 gate 阶段构建的默认情境继续
    - 保留诊断日志记录 LLM 决策结果，便于观察 LLM 倾向
  - **验证**:
    - `ruff check engine_peer_chat_support.py 通过`
  - **备注**:
    - 设计原则：gate 是唯一决策入口，gate 通过 = 必须发送。LLM 决策只辅助不阻断
    - 之前已修复的概率问题：base_probability 0.04→0.08，_BUSY_PEER_PROBABILITY_MODIFIER 0.4→0.6
    - 之前已修复的 SLEEP_RECOVERY 未加入 CHAT_ELIGIBLE_ACTIVITIES 问题
    - 之前已修复的协商检查不执行问题（在 CharacterDailyEngine._tick 中接管）

## 2026-07-07（修复 /打断 命令的提示问题）

- **修复 /打断 命令后角色不知道被中断了什么活动，以及不处理累积消息**
  - **问题1**: 用户使用 `/打断` 命令打断角色学习后，角色回复说"CPU才6%，闲得很"，表示自己没在学习。但系统日志显示"已打断 aveline 的 studying"，说明系统知道角色在学习，但角色自己不知道。
  - **问题2**: 角色被打断后，回复时没有之前被静默累积的消息上下文。用户在角色学习时发送的消息应该被累积起来，打断后角色应该知道这些消息。
  - **根因1**: `reply_policy.py` 的 `evaluate_reply_state` 函数在命中手动打断窗口时，使用的是当前活动状态（通过 `engine.get_current_activity` 获取），而非中断窗口中记录的 `activity` 字段（被中断的活动）。
  - **根因2**: 手动打断窗口处理返回的 `ReplyDecision` 没有设置 `accumulated_messages` 字段，导致 chat_handlers 无法处理累积消息。
  - **修复**: 
    - 从中断窗口中读取 `activity` 字段，转换为 `ActivityType` 后传给提示生成函数
    - 如果有累积消息，使用 `build_busy_interrupt_hint` 构建包含累积消息的提示
    - 在 `ReplyDecision` 中返回 `accumulated_messages=list(accumulated_messages)`
  - **文件**: `core/services/character_daily/reply_policy.py`
