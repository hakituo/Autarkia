## 2026-07-06（周一）
  
  - **修复 send_ping 在 FastAPI WebSocket 上报 'string indices must be integers' 错误**
  - **背景**: 心跳检查器启动后，日志中持续出现 'Failed to send ping to 127.0.0.1: string indices must be integers' 警告，导致 ping 永远发不出去，60 秒后心跳超时清理连接，QQ adapter 重连后循环重演，给用户造成'网络不好'的错觉。
  - **根因**:
    - Starlette WebSocket.send() 期望 ASGI dict 格式（message["type"]），不是字符串
    - heartbeat_service.py 的 send_ping 直接用 websocket.send(ping_data) 传字符串，触发 'string indices must be integers'
    - message_sending.py 已经用 hasattr(websocket, 'send_text') 做了兼容判断，但 send_ping 没有同步处理
  - **修复**:
    - heartbeat_service.py: send_ping 中添加 hasattr(websocket, 'send_text') 判断，FastAPI WebSocket 走 send_text，websockets 库走 send
  - **验证**:
    - `新增 2 个回归测试：test_send_ping_uses_send_text_for_fastapi_websocket 和 test_send_ping_uses_send_for_websockets_lib`
    - `28 个测试全部通过`
  - **备注**:
    - 用户日志确认修复前现象：连接建立 60 秒后被 'Heartbeat timed out' 清理，QQ adapter 重连，循环不止
    - 此 bug 是上一个修复（启动心跳检查器）暴露出来的：心跳检查器之前从未启动，所以 send_ping 的兼容问题一直被隐藏

- **修复 WebSocket 心跳检查器未启动导致长期运行后连接被拒问题**
  - **背景**: 用户反馈后端开久之后再开 QQ adapter 就连不上。诊断发现心跳检查器从未启动，僵尸连接累积耗尽 max_connections=50 配额，新连接被 add_connection 拒绝。
  - **根因**:
    - WebSocketManager.running 始终为 False，无任何位置将其设为 True
    - heartbeat_checker 协程定义了但从未被 create_task 启动
    - initialize_websocket_manager() 函数无调用方
    - FastAPIWebSocketAdapter.initialize() 获取了 websocket_manager 但未调用 initialize()
  - **修复**:
    - websocket_manager.py: initialize() 中添加 self.running = True 和 create_task(self.heartbeat_checker())
    - adapters/adapter.py: initialize() 中调用 await self.websocket_manager.initialize()
    - adapters/adapter.py: shutdown() 中调用 await self.websocket_manager.stop()
  - **验证**:
    - `新增 4 个测试验证心跳检查器启动逻辑（test_android_client_bugs.py::TestWebSocketHeartbeatStartup）`
    - `26 个测试全部通过`

- **修复角色晚安消息未送达 QQ 的 bug**
  - **背景**: 用户反馈 AI 角色睡觉时没有发晚安消息。排查日志发现 2026-07-05 23:10 和 23:40 都成功触发了 goodnight_proactive 消息生成，但消息只存入离线队列，QQ 端从未收到。同时 ling 的晚安消息被错路由到 aveline 的会话。
  - **根因**:
    - trigger_character_goodnight 调用 executor.trigger_message() 时未传 client_type="qq"
    - dispatch_proactive_message 中 if client_type == "qq" and "__persona__" in target_conversation_id 条件不成立，broadcast_user_id 未剥离 __persona__ 后缀，ws_manager.broadcast 找不到连接 → 消息只能存离线队列，QQ 实时收不到
    - resolve_target_conversation 因 client_type 为空，is_qq_client=False，不走 persona 路由，直接用 resolve_primary_conversation_id() 返回的主会话（aveline 的），导致 ling 的晚安被错发到 aveline 会话
  - **修复**:
    - core/services/active_care/goodnight_proactive.py: trigger_character_goodnight 调用 executor.trigger_message() 时补传 client_type="qq"，并加注释说明不传会引发的两个连锁问题
    - tests/scripts/active_care/verify_character_goodnight.py: 在 test_trigger_character_goodnight_delivers_and_marks_sent 和 test_sleep_again_uses_sleep_again_sys_prompt_type 中新增 client_type="qq" 断言
