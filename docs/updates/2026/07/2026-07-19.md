## 2026-07-19（周日）

- **修复夜间异步任务 600s 超时误杀与 error_collector 合成 RuntimeError 误报**
  - **背景**: errors_20260719.json 报告 memory/nightly/task_runner.py:62 抛出 RuntimeError 但 traceback 为空、error_message 在冒号后为空。回查 logs/2026/7/19/xiaoyou_main.log 发现 02:31:51 启动夜间任务，02:41:51 抛错，正好 600 秒——这是 future.result(timeout=600) 超时，并非真实 RuntimeError。瓶颈在 PeopleProfileExtractor 串行处理 28 批次耗时 9 分 11 秒。
  - **根因**:
    - run_nightly_async_tasks 用 future.result(timeout=600) 调度跨线程协程，夜间任务（蒸馏→人物档案→日记→明日计划→MEMORY.md 瘦身）串行执行，250+ 条消息/28 批次人物档案提取单用户即可超过 600s，超时后日记生成等后续步骤被误杀
    - except Exception as exc 分支的 logger.error 未传 exc_info=True，error_collector._schedule_report 在 record.exc_info 为 None 时兜底执行 RuntimeError(record.getMessage())，导致 errors_*.json 中 error_code 误报为 RuntimeError、traceback 显示 NoneType: None
    - Python 3.10.11 下 concurrent.futures.TimeoutError 与内置 TimeoutError 不是同一个类（Python 3.11+ 才别名），未显式 import concurrent.futures 并捕获其 TimeoutError 时，超时会落入通用 except Exception 分支，难以与真实业务异常区分
  - **修复**:
    - memory/nightly/task_runner.py 新增类常量 NIGHTLY_TASK_TIMEOUT_SECONDS=1800，覆盖最慢用户的人物档案提取场景
    - 显式 import concurrent.futures，新增 except concurrent.futures.TimeoutError as exc 分支并放在通用 except 之前，超时返回空 dict 且不取消底层协程（避免半成品数据）
    - 两个 except 分支的 logger.error 均带 exc_info=True，错误消息含 user_id、exc_type=type(exc).__name__、exc={exc} 字段，确保 error_collector 拿到真实异常类型与栈
  - **验证**:
    - `venv_core/Scripts/python.exe -m ruff check memory/nightly/task_runner.py`
    - `venv_core/Scripts/python.exe -m py_compile memory/nightly/task_runner.py`
    - `venv_core/Scripts/python.exe tests/scripts/verify_nightly_task_timeout_fix.py（6 项检查全通过）`
  - **备注**:
    - 不调用 future.cancel()：run_coroutine_threadsafe 的设计行为是底层协程仍在主 loop 上运行，日志证实 02:42:07 明日计划仍在生成，强行取消可能留下半成品数据
    - CODING_GUIDE.md 6.2 节规范要求 ERROR 级别日志必须带 exc_info=True，本次同时修复了规范违规
