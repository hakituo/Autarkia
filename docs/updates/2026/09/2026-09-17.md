- **History 接入 SQLite 派生索引：搜索 / 最近记录 / 事件点查不再随总历史量线性变慢**
  - **背景**: 承接 P0-P2（`27fdc9b5`）之后的专项计划 `PLAN_history_sqlite_memory_perf.md` §1-§2。P0-P2 已经消掉了"每条消息重建当天 index.json""recent-N 全历史 rglob""People 扫全树"等无界工作，但仍有一批路径每次都重新解析全部 JSONL：搜索工具的同 scope 扩展搜索每搜一次就把整个 scope 的所有 `.jsonl` `rglob` 出来逐行 `json.loads`（H2）；peer 搜索扫所有 chat_history root（H3）；带关键词的 `list_conversation_events` 无法日期早停（H1）；`get_event_content` 顺序读整个文件找 event_id（H4）；Memory 启动回填按天读文件（H5）。这些成本都随累计历史线性增长。
  - **根因**:
    - JSONL 作为唯一真源没有问题，但缺一层派生索引，"每次查询 = 重新解析全部真源"的模型注定随数据量线性变慢。
    - 中文搜索不能简单换 FTS5：实测本机 FTS5 trigram 对 <3 字查询不命中，而 jieba 切出的中文词元大量是 2 字（"初中""女生""火锅"），上 FTS5 会让这类高频查询直接漏召回，质量劣于现状。
  - **修复**:
    - 新增 `core/services/chat_history_index.py`：per-scope SQLite 派生索引（`SCHEMA_VERSION=1`），薄生命周期接口 `rebuild / health / clear / append_events / ensure_sync / delete_conversation / delete_file / query`，模块级注册表 `get_history_index / reset_history_index_registry / rebuild_history_index`。DB 落 `companion_data/{scope}_data/indexes/chat_history.db`（自定义 `base_dir` 同规则派生，不硬编码 scope）；`user_version` 不匹配即 drop 重建，绝不按旧结构读。
    - 增量同步：`append_event` 在 JSONL 与 day index 写完后单事务 `INSERT OR IGNORE` + **有条件的偏移推进**——只有"本次 append 前该文件已完整同步到 `expected_bytes`"才把 `files.synced_bytes` 推到位，否则保持原值交给 `ensure_sync` 从头 tail 读，避免"只索引了新行却声称整个文件已同步"丢历史。DB 写失败吞异常 + warning + `mark_stale()`，append 返回值与现状完全一致。

- **保存耗时归因：Python 侧只占 ~110ms，其余是「每文件一次 fsync」**
  - **背景**: 上一段测出保存最大主体 0.40~1.26s 后，需要判断这笔开销该往哪儿优化——是 Python 侧的逐条 normalize / 序列化，还是 IO 本身。这决定了「改代码」和「改持久化格式（§6）」哪个才是对的解法。
  - **测量**（`shared__scope__ling`，4194 条 / 序列化 13.57MB，各取 3 次最小值）:

    | 环节 | 耗时 |
    |---|---|
    | compaction（逐条 `_compact_weighted_memory_record`，含 `_normalize_memory_record`） | **33.4ms** |
    | `json.dumps`（不含 IO） | **78.3ms** |
    | 上述之外（文件写入 + fsync + 原子替换 + 临时文件清理） | **约 300~1150ms** |

  - **结论**:
    - **Python 侧只占 ~110ms（约 10%~25%）**，把序列化搬出锁、减少逐条 normalize 之类的改动最多只能省下这一小块。
    - 真正的大头是 IO，且 `core/utils/atomic_io.py::safe_json_dump` 是**每个文件都无条件 `f.flush()` + `os.fsync()`**，保存 6 个 category 文件就是 6 次（加上目录替换可能更多）约 2.3MB 的 fsync —— Windows 上 `FlushFileBuffers` 的固定开销被放大了 6 倍。

    - 保存整段持的是**读锁**（`safe_save_all` → `get_read_lock`），所以并发**检索不受影响**，被挡住的是并发**写入**；活跃聊天里记忆写操作可能因此被推迟最多约 1.3s。
  - **未做任何改动**：这里有两个候选方向，都属于「改持久化/持久化语义」的范畴，超出计划 §6「仅设计不动格式」的边界，需要单独决策：
    - ①把 6 个文件的 fsync 合并成一次（先全部写完再统一 fsync）——格式不变，但改变了崩溃一致性窗口；
    - ②去掉 `indent=2`——格式（空白）变化，JSON 语义不变，可省 20%~30% IO。
    - 计划 §6 的 `snapshot + mutation journal` 解决的是"全量重写"这件事本身，收益更大但影响面也最大（加载/保存/迁移/回滚都要动）。
