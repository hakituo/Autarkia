- **「更多」二级板块的手势归属与返回层级：横滑翻上一天/下一天，返回键先退回「更多」**
  - **背景**: 上午那条「二级板块里横滑会把『更多』整页滑到『专注』」只做了前半件事 ——

    「外层 pager 翻到首页后没人要的横向手势」（手势接力）。pager 手势一关，
    子页面里没有任何节点消费横向位移，于是全部被抽屉收走。

      父层 `anchoredDraggable` 不再触发；同时挂一条只在 `onPostScroll`（子层之后）
      吃掉横向位移的 `NestedScrollConnection`，把抽屉的第二条通路（scrollable 冒泡）

- **Windows Proactor accept 瞬态噪音治理：不再刷 ERROR 堆栈，监听也不会被顺手关掉**
  - **背景**: 启动服务后日志出现 asyncio 的 ERROR：先一条 Task exception was never retrieved（accept_coro 抛 OSError(22, '指定的网络名不再可用。', None, 64)），紧跟一条 Accept failed on a socket（socket 为监听地址 0.0.0.0:8000），两条都带完整 traceback，出现在月度总结补跑日志之后、服务刚起来的时刻。这类报错会被日常日志反复刷，掩盖真实故障。
  - **根因**:
    - 客户端在服务器完成 accept 之前断开（端口探测、健康检查、移动端网络切换、客户端超时重连），Windows 的 AcceptEx 因此返回 WinError 64（ERROR_NETNAME_DELETED，指定的网络名不再可用）——本质是对端断开的瞬态噪音，不代表服务异常。
    - CPython 的 BaseProactorEventLoop._start_serving 把它当真实故障处理：accept future 的 f.result() 抛 OSError 时先 call_exception_handler('Accept failed on a socket') 打 ERROR + 堆栈，紧接着 sock.close() 关闭监听 socket。此后 accept 循环只能在已失效的 socket 上静默失败——进程还活着、端口看起来还在，但再也接不了新连接。这是比日志噪音严重得多的隐患。
    - accept 的 future 异常无人取回（负责它的 accept_coro 任务无人持有引用），任务析构时触发 loop.call_exception_handler('Task exception was never retrieved')，于是同一个错误再打一条 ERROR——正是用户日志里的两条报错。
    - uvicorn 在 Windows 上强制 Proactor（config.setup_event_loop），core/interfaces/websocket/websocket_manager.py 里那句 WindowsSelectorEventLoopPolicy 会被覆盖，所以项目里并没有现成的规避路径。
    - main.py 的 _run_server 直接调 uvicorn Server.run()，它内部 asyncio.run 不给插入点，没有地方能装事件循环异常处理器。
  - **修复**:
    - 新增 core/utils/asyncio_accept_noise.py：install_proactor_accept_patch() 用修正版 _start_serving 替换 Proactor 的实现——瞬态网络错误（WinError 64/995/10038/10053/10054/10058）只记 debug 并继续 accept，不关闭监听 socket；非瞬态错误保持原生行为（上报 + 关闭 + 结束循环），真故障不会被藏起来。
