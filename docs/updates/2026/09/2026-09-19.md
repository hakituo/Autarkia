- **给可缓存前缀加逐块指纹日志：不用再猜"前缀断在哪一块"**
  - **背景**: 上一轮靠推理把"前缀断裂"归因到检索资料块，但实测发现

    carryover 与学习/聊天模式。9-18~19 主日志实测：2~17 个工具不等，
    schema 中位字符 414（1 个）→ 2285（3 个）→ 9188（12 个）→ 11588（17 个）。
    按「工具集相对上一请求是否变化」分组（n=385）：不变 加权命中 **67.5%**、钉底座 46%；
    变了 加权命中 **55.8%**、钉底座 55%。差约 12 个点，但**有混淆**
    （换话题/换会话也会同时换工具），且 prompt_tokens 只随 schema 增长约一半，
    所以工具 schema 是否算进可缓存前缀**尚未证实**——这正是把 `tools`
    加进指纹的目的，等一天数据来定案。
  - **验证**: `verify_full_static_prompt.py` 的

    改静态层只动 system、换历史首条只动 hist0、工具集变了动 tools、
    工具名顺序不影响指纹）。`ruff` 通过。
  - **用法**: 数据只要 grep `PromptCacheSig`，按角色看相邻两行哪一段在跳，

- **多角色共用一个 OpenRouter 模型时缓存会不会互相破坏：不会，但 TTL 才是真风险**
  - **结论（依据 OpenRouter 文档原文）**: sticky routing 是 **account + model + conversation**
    三级粒度，"conversation" 由**首条 system/developer + 首条非 system** 的哈希识别。
    不同角色的人设不同 → 会话键不同 → 天然落到不同 provider，各自保暖、互不挤占。
    所以 A 聊完去聊 B，不会冲掉 A 的缓存。

    1. **TTL 短**：Anthropic 默认 5 分钟，Gemini 固定 5 分钟且"不刷新"。

       （本次默认仍是 5 分钟，是否改默认由业务侧定）。
    2. **sticky 会话 10 分钟无活动即失效**，之后可能被路由到别的 provider（冷启动）。
    3. **provider 侧缓存容量是共享的**，上游繁忙时被挤掉会退化成部分命中
       （前面 DeepSeek `:free` 那个 21.7% 就是这个现象）。

    改成**只用首条 system/developer**。
    原因：本项目的消息布局是 `system(静态人设) + user(working_set 资料召回) + 历史 + 尾巴`，
    首条非 system 是**每轮都可能变**的召回结果；按 OpenRouter 默认口径算，
    同一个角色的 sticky 绑定会反复漂移，等于每轮都可能被丢到没缓存的 provider。
    只用静态人设当键，"一个角色 = 一个 provider"才稳定。
    没有 system 时退回首条消息，保证始终有稳定键。
  - **验证**: 新增 3 条单测（换 working_set / 换尾巴不影响 session_id；

## 2026-09-19（星期六）全量静态前缀实验：实测后判定无意义，已整体删除

### 结论：删除

`persona_full_static_prompt` 全量注入实验**整体删除**（模块、接线、配置项、验证脚本）。
判定依据不是主观感觉，是实测每个角色「开 vs 不开」到底差哪一段内容。

### 实测：各角色「关闭时检索到的资料块」vs「全量块」

| 角色 | 全量块 | 关闭时检索到的 | 资料文件 | topic 数（全量块内） |

### 为什么判定无意义

1. **它不是省钱方案，是绕过检索的笨办法**。资料进不去的角色（ye 完全为 0、
   lin 大部分提问为 0），全量只是把源文件硬塞进 system；而真正该修的是检索配置。

3. **对 ling 是稀释**：她关闭时只进 `food_and_drink` 一个 topic（530 字符），
   全量会多灌 9 个 topic（审美、外貌、传记、教育、家庭、游戏、社交、工作消费…），
   注意力被摊薄，而多数话题用不上。
4. **对 aveline 完全无效**：`knowledge=None`，全量块为空，开与不开字节级一致。

- **auto_commit_push 增加重复提交保护**
  - **背景**: 今天多次出现「一条命令生成两个同名 commit」：第二个只含记忆文件的重复追加。

  - **背景**: 用 `--only` 提交且指定范围内已无改动时，脚本仍会走到 `git commit`，
