- **Android：修「开流量不切公网域名」与「点发送卡一下才发出去」**
  - **背景**: 用户反馈两件事——(1) 后端同时监听局域网入口和 Cloudflare Tunnel 公网入口，

    要卡一会儿消息才出去。
  - **根因（网络切换，四处叠加）**:
    - `EndpointResolver.resolve()` 的候选顺序**写死为「局域网优先」**。蜂窝网络下
      `192.168.x.x` 物理上不可达，先探它必然白等一个 connect 超时
      （`LAN_CONNECT_TIMEOUT_MS = 800`），这段等待直接叠加在「出门切公网」的体感上。
    - `startMonitoring()` 只重写 `onAvailable`。蜂窝网络通常**早就是 available 状态**，
      从 WiFi 切蜂窝时默认网络对象可能不换、只有链路类型变，回调只走
      `onCapabilitiesChanged`；「WiFi 连着但没 Internet 校验」同理。只盯 `onAvailable`
      就可能出现「网络确实变了，但裁决器一次都没重探」。
    - 缺少物理兜底：所有候选都没探通时一律沿用旧地址。蜂窝下旧地址是家里内网 IP 时，
      这是 100% 发不出消息的状态，而公网只是「这次没探通」（隧道冷启动、
      健康检查偶发慢都会导致）——一次探测抖动就把用户整段出门时间锁死在内网地址上。
    - `WebSocketManager.scheduleReconnect()` 里 `attempt >= 1` 才重探，出门后第一次
      重连仍按已经不通的内网地址硬试一轮。
    - 附带：公网域名槽位 `tunnelUrl` 为空时没有任何提示，排查「为什么切不过去」
      只能翻代码。
  - **根因（点发送卡）**:
    - `ServerDiscoveryManager.discoverServer()` **不判断网络类型就做子网扫描**：
      9 个子网 × 254 个地址，每个最多等一个连接超时，并发 30。蜂窝网络下这些地址
      一个都不可能通，整轮要空转几十秒，还会把 `Dispatchers.IO` 线程池占满——

  - **背景**: 上一条修完后用户实测反馈三点：(1) 设置页点「重新检测」**永远**提示

    即上一条加的「蜂窝 + 私网地址强制降级」只是让症状不那么绝对，主因没找到。
  - **根因（实测确认）**: 两个探测调用点（`EndpointResolver.probe` 与
    `ServerDiscoveryManager.verifyBackendIdentity`）都写着「只读响应体前 1024 字符判断身份，
    避免拉整个 body」，而 `/api/v1/health` 的 payload 顺序是
    `status` → `services`（一整坨服务明细）→ `metrics` → `timestamp` →
    `service: "AI Agent Core"` → …。实测本机后端响应：**总长 5470 字节，
    `AI Agent Core` 的偏移是 1058**——刚好在 1024 之外 34 个字符。
    于是所有候选地址一律被判「不是我们的后端」，`resolve()` 永远返回 null：
    - 设置页重探：走完探测只能报「所有候选地址都不可达」（地址其实是好的）；
    - 开流量：`resolve()` 全失败 → 保留旧地址，只有失败重连里的强制降级分支能救，
      而那条路径要等 WS 重连 + 探测超时（600ms 去抖 + 3s+3s 公网超时）才走到，
      所以「能切但很慢，还常常要重启」；
    - 回家：WiFi 下 `resolve()` 同样全失败，且不满足「蜂窝 + 私网地址」的强制降级条件，
      于是**永远沿用公网地址**，局域网再也切不回来；
    - 连带：`ServerDiscoveryManager` 的自动发现也依赖同一判据，所以它**从来没成功过**
      → `lanUrl` 槽位长期是空的 → 即使探测修好，WiFi 下也没有局域网候选可切。
  - **修复**:
    - 新增 `services/endpoint/BackendIdentityProbe.kt`：把身份判据收敛成唯一实现
      （`HEALTH_PATH` / `HEALTH_MARKER` 常量也一并收拢），改为**分块读到 marker 出现为止**
      （块 4096 字符，上限 256K 字符），并用 12 字符的尾部重叠处理 marker 被切在块边界的情况。
      顺带区分日志：HTTP 401/503 记「地址可达但未通过认证」，与「连不上」分开，

  - **背景**: 用户局域网直连（后端日志里客户端就是 `192.0.2.134`），在聊天页点发送，

  - **现场证据**（`logs/2026/9/18/server.log` 与 `xiaoyou_main.log`）:
    - 三个 POST 几乎同时到达：`09:41:29,306` / `,309` / `,316`（间隔 3~7ms），
      三个请求正文长度都是 37、会话都是 `web_role_aveline` —— 用户点三次，
      **三条请求是一起被放出去的**，不是逐个发。
    - 紧挨着它们之前，`09:41:29,287` 有一条 `GET /api/v1/personas` 返回，
      耗时 **1.32 秒**（`慢请求警告`）。同一分钟里 `/api/v1/personas` 还出现过

    1. `ChatSendController.sendMessage()` 在**清空输入框、上屏气泡、置 `isTyping` 之前**

       （01:50 的 18399c4 已经把「清输入框 / 乐观上屏」提前了，但只提前到

- **修复 Android 通知体验：套娃 + 通知不清 + "找不到人设"**
  - **背景**: 用户反馈两个问题：
    1. 切回 App 看消息，通知**不会自动消失**（只有点通知进聊天页才清）；
    2. 点通知会**新开一个聊天页**（套娃），即使当前已经在和这个角色聊天；
    而且在新开的页面里发消息会**提示"找不到这个人设"**。
    主动关怀的通知也有套娃问题。
  - **根因 1（找不到人设）**: `RoleReplyNotifier.chatDeepLink()` 生成 `aveline://chat?session_id=...`，
    但 `NavGraph` 的 chat 目的地只声明了 `text`/`role`/`filename`/`name` 四个 argument，
    **没有 `session_id`**。系统把该深链匹配到最宽泛的 `aveline://chat`，四个参数全为空
    → 聊天页拿不到人设 → "找不到这个人设"。
  - **根因 2（套娃）**: `MainActivity` 的 `LaunchedEffect(deepLink)` 里
    `navController.navigate(route)` 无条件执行，不检查当前是否已在同角色聊天页。
  - **根因 3（通知不清）**: 撤通知只在 `ChatSessionController.clearUnreadForRole()` 里，
    而该方法只在**会话切换/初始化时**调用；用户切回 App（角色没变）时不会触发。
  - **修复**:
    - `RoleReplyNotifier` 去掉 `session_id` 深链分支，统一只发 `role`+`filename`
      （与 NavGraph 声明严格对齐）；同时新增 `visibleChatRole`/`visibleChatFilename`
      原子引用 + `markChatVisible`/`clearChatVisible`/`isChatVisibleFor`/`cancelNotificationsFor`
      四个方法，作为"当前聊天上下文"的共享注册表。
    - `NavGraph` 的 chat composable：进入时 `LaunchedEffect` 登记可见角色
      （`targetRole` 为空时退化为 `markVisibleChat`），离开时 `DisposableEffect`
      清空登记。
    - `ChatViewModel` 新增 `markVisibleChat`/`clearVisibleChat` 代理方法；
      `setPendingSwitch` 内同步调 `markChatVisible`。
    - `MainActivity` / `AvelineApp`：
      - 点通知深链时先 `replyNotifier.isChatVisibleFor(role, filename)` 判断：
        若已在同角色聊天页，只 `onDeepLinkConsumed()` 不 `navigate`，避免套娃。
      - 新增 `AppForegroundTracker.isForegroundFlow` 监听：切回前台且当前停在聊天页时，
        自动 `cancelNotificationsFor(visibleRole, visibleFilename)`，通知自动消失。
    - 注入 `replyNotifier` 到 `MainActivity` 和 `AvelineApp` 参数链。
  - **验证**: 待编译验证（Android Studio）。
  - **备注**: 深链参数必须与 NavGraph 声明严格对齐；`session_id` 虽然能切会话，
    但导航层不认识它时就会退化成空参数 → 这是"找不到人设"的直接原因。

- **修复 Android 断句时好时坏：模型一用 markdown，整条回复就退化成一个大气泡**
  - **背景**: 用户反馈安卓端「一会能正常断句，一会不能正常断句」。抓当天主线对话
    （`companion_data/aveline_data/chat_history/2026/09/18/主线对话/web_role_aveline.jsonl`）
    的 assistant 消息复现：同样都是讲解文言句式的短回复，有的切成 3~4 个气泡，
    有的整条挤在一个气泡里、换行原样显示成多行。
  - **根因**: `TextSegmenter.splitForDisplay()`（Python 端 `split_for_display` 同源）
    的 markdown 守卫是**全有全无**的——只要全文**任意位置**命中
    `^\s{0,3}(?:```|~~~|#{1,6}\s|[-*+]|\s|>)`、`\|.*\|` 或 `$$`，就 `return listOf(cleaned)`
    整条透传，一个气泡都不切。
    模型这一轮只要用了一个 `- ` 列表项（讲解里极其常见），整条回复就走透传分支；
    下一轮没用 markdown，就正常断句。断句结果取决于「模型这次有没有用 markdown」，
    而不是文本本身。
    实测复现（修复前气泡数）：1 / 3 / 7 / 1 / 4 —— 波动即来自这里。
  - **根因 2（顺带发现）**: 断句器按标点切分，而加粗里可以自带句号。
    `**古之人 / 不 / 余 / 欺。**` 被切成「`**古之人 / 不 / 余 / 欺`」+「`** 顺便…`」，
    两段各剩一个 `**`，渲染时星号落单、原样显示出来（用户截图里可见）。
  - **修复**:
    - `core/utils/text_segmenter.py`：新增 `_group_display_lines()`，把「全有全无守卫」
      换成**按行结构分组**——只有跨行连续结构（代码围栏 / `$$` 块公式 / 连续表格行）
      和单行块级标记（标题 / 列表项 / 引用 / 含 `$$`）整组保留；普通段落行照常交给
      `split_chat_message()` 按标点切气泡。整组保留的块不再二次 strip，避免吃掉代码
      末尾的点。新增 `repair_broken_inline_spans()`：检测未闭合的 `**` / 反引号，

    - Kotlin 端同步：`utils/text/TextSegmenter.kt` 新增 `groupByStructure()` /

    2. `$$...$$` 只有**整行以 `$$` 开头**时才被 `MarkdownBlockParser` 认成块公式；

       直接 `buffer.append("$$")`，于是子项里的块级公式原样吐出两个美元符号。
       行内 `$F=ma$` 一直是好的，所以现象是「有的公式能渲染、有的不能」。
