## 2026-09-27（周日）

- **聊天记录按渠道标注来源：QQ 历史不再与 App 历史混为一谈**
  - **背景**: 同一个 conversation_id 里混着多端产生的记录：从 QQ 导出后导入的历史、QQ bot 的实时对话、App 的实时对话、Obsidian 等。它们共用一份 chat_history 与同一个加权记忆池，但来源信息只写不读——导入器写的 platform / imported / source_kind 在运行时没有任何消费方，history_fetch 里的平台标注还显式把 qq 排除（`if _pf and _pf != "qq"`），search_chat_history 也只按 platform 过滤、返回结果不带来源字样。结果是模型分不清『这条是 QQ 上说的』还是『刚刚在 App 里说的』，也完全不知道自己此刻在哪个渠道。
  - **根因**:
    - 渠道信息只写不读：metadata.platform 仅被搜索过滤消费，source_kind / imported 全仓无消费方
    - 历史清洗显式排除 QQ，只给 Obsidian 加『（来自Obsidian）』标注，QQ 记录进上下文时没有任何来源字样
    - 没有任何地方告诉模型『当前渠道』，因此即使标了 QQ，模型也无法把『没标的』正确理解成本渠道
    - 判据不能只看单一字段：实测 pairs 导入器只写 imported 不写 platform（13768 条），QQ bot 早期记录只能靠 readable_title 车道名判定（约 7800 条），lin 的 18374 条 QQ 历史还落在『主线对话』车道里，按车道名判断同样会漏
  - **修复**:
    - 新增 core/utils/data/chat_channel.py：resolve_event_channel 三级判据（platform → imported / source_kind → readable_title 车道名 → 默认 App）、channel_display_name、source_suffix（与当前渠道相同时返回空串）、strip_source_suffix 幂等保护，以及用 ContextVar 携带『当前渠道』的 set / get / reset（与 message_branch 同一套路，避免把 platform 逐层透传穿过 stream_chat → context → assembler → 工具执行）
    - ChatAgent.stream_chat 在生成前 set_current_platform(platform)：这是所有流式回复（主对话 / 问候 / 主动消息）的唯一入口，platform 已由 WS 连接或 HTTP 路径带入；非流式与后台任务回落 App
    - history_fetch.sanitize_history_messages 增加 current_platform 参数：与当前渠道不同的历史消息追加『（来自QQ）』后缀，与当前渠道一致时不标（App 上看 App 历史零噪音）；重复清洗先剥再补，不叠加
    - 从 ChatHistoryStore 回填历史时把 readable_title / imported / source_kind 一并带出，否则 pairs 导入与车道名兜底都判不出来源
    - assembler 在『当前时间』旁注入『当前渠道：App / QQ』，并且只在历史里真的出现跨渠道记录时才补一句『带（来自…）后缀的消息来自 QQ，不是当前渠道』，纯同渠道场景不多说一句
    - search_chat_history 的普通检索与 peer 检索结果都按同一规则追加来源后缀，模型自己翻到的 QQ 记录同样带标注
