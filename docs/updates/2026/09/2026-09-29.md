- **清洗模型自己复述出来的渠道标注（（来自QQ）/ 来自App）**
  - **背景**: 昨天给跨渠道历史消息加了「（来自QQ）」后缀后，模型开始照着这个格式自己复述：主动消息与对话回复里冒出「（来自App）」「来自QQ」这类对用户毫无意义的尾巴，需要剥离。
  - **根因**:
    - 「（来自X）」原本是系统给历史消息加的标注（chat_channel.source_suffix），进模型上下文后模型把它当成说话格式模仿
    - core/utils/data/chat_channel.py 只有 strip_source_suffix，且只认全角括号 + 句尾一种形态，仅用于历史清洗的幂等剥离，没有任何一处清洗模型输出
    - 输出清洗分散在四条链路（流式 / 非流式 / 主动消息 pipeline / QQ adapter），此前没有一处处理渠道标注
  - **修复**:
    - core/utils/data/chat_channel.py 新增 strip_model_channel_marks：剥离全角「（来自QQ）」/ 半角「(来自App)」/ 句首句中出现 / 句尾裸写「来自手机」四种形态；渠道名走白名单（与 _DISPLAY_NAMES 同步）且要求后接空白或句读，因此「来自QQ音乐」「（轻轻揉了揉眼睛）」不会被误伤，剥完顺带折叠多余空白与叠加标点
    - 流式主链路：core/agents/chat_agent_components/streaming_pipeline/postprocess.py 新增 strip_channel_marks 并接入 postprocess_response（排在时间戳剥离之后），覆盖 App / Web / QQ / Telegram 全部实时对话
    - 非流式链路：core/agents/chat_agent_components/handler_postprocess.py 在时间戳剥离后调用同一函数，final_content 与由其分叉的 full_content（TTS / 落库）一起清洗
    - 主动消息：core/services/active_care/postprocess/pipeline.py 新增 ChannelMarkStripStep，插在 TagSanitizeStep 之后、EmptyAfterStripCheckStep 之前（避免「整条只剩一个后缀」剥完变空还漏过空检），并同步清理 full_raw_text 防止 TTS 把「来自QQ」念出来
    - QQ adapter 按既有惯例复用 core 实现：clients/bots/qq/utils/text_cleaners.py 从 core 导入并导出（与 strip_ai_timestamp 同一处），clients/bots/qq/session/message.py 的 send_full_response_with_split 清洗链在时间戳剥离之后调用它并记录日志

## 2026-09-29（周二）

- **工具调用标记（DSML token）泄漏到正文：解析层容错 + 四条输出链路兜底剥离**
  - **背景**: 在与 Aveline 的真实对话记录里发现工具调用协议标记（全角竖线组成的 DSML token，如 <｜｜｜DSML｜｜｜ calls>）被原样发给了用户。核查后确认是模型吐出的 token 形态漂移导致解析层认不出、两个流式检测点也不缓冲，原始 token 就当成可见正文流出去了。
  - **根因**:
    - 模型确实决定调用工具，但吐出的 token 形态漂移：容器名丢了 tool_ 前缀（只写 calls）、前缀与标签名之间多了一个空格、开闭标签空白不一致
    - dsml_parser 用原样字符串拼接匹配（<｜｜｜DSML｜｜｜tool_calls> 这类固定写法），漂移形态 detect_dsml_format 返回 None，has_dsml_tokens 为假，response_parser 的兜底分支根本不进入
    - 两个流式检测点（dsml_stream 的 chunk 缓冲、tag_stream_parser 的可见文本扣留）各自维护一份重复的字符串标记列表，同一套窄口径，漂移形态不被扣留，token 直接流给用户（tag_stream_parser 才是用户看到的实际泄漏路径）
    - DSML 兜底此前只存在于流式链路一步（clean_dsml_residue，且只「剥」不「跑」），非流式 / 主动消息 / QQ adapter 三条链路完全没有这一步
  - **修复**:
    - core/llm/openai_compat/dsml_parser.py 重写识别口径为容错正则：前缀与标签名之间允许任意空白、容器名接受 tool_calls / function_calls / calls、开闭标签各自独立容忍空白；新增 strip_tool_mark_residue 通用清洗，覆盖完整漂移块 / 未闭合块 / 被拆到多条消息的裸残片 / 只剩裸前缀四种形态（无标记时原样返回，便于调用方用 after == before 判断是否记日志）
    - core/llm/openai_compat/dsml_stream.py 的 DSMLStreamFilter 改用容错起止正则，新增 _partial_opener_index 扣留被截断的开标签、新增 flush() 收尾（未闭合的缓冲按可见文本吐出，避免整段内容被吞）；client.py 在流式循环结束后补 dsml_filter.flush()
    - core/agents/chat_agent_components/streaming_pipeline/tag_stream_parser.py 删除本地重复的 DSML 字符串标记列表，改为复用 dsml_parser 的容错正则，漂移形态在解析阶段就被扣留
    - 输出侧接入四条链路：流式 postprocess.py 的 clean_dsml_residue 改调 strip_tool_mark_residue；非流式 handler_postprocess.py 在渠道标注剥离之后新增一行调用（final_content 与由其分叉的 full_content 一起清洗）；主动消息 pipeline.py 新增 ToolMarkStripStep 插在 ChannelMarkStripStep 之后、EmptyAfterStripCheckStep 之前（避免整条只剩 token 时剥完变空还漏过空检），并同步清理 full_raw_text 防止 TTS 念出 token
    - QQ adapter 按既有惯例复用 core 实现：clients/bots/qq/utils/text_cleaners.py 从 core 导入并 re-export，utils/__init__.py 同步导出；session/message.py 的 send_full_response_with_split 与 transport.py 的 send_to_napcat 清洗链都在渠道标注剥离之后调用（transport 是流式 chunk 直发路径的最后一道发送防线）
    - clients/bots/qq/transport.py 顺手删掉一行过时的「不再需要过滤剧本标记前缀」注释（属于已拆分的死注释，同时该文件改动后行数触顶，一并腾出行数）
