- **安卓端聊天输入框草稿持久化：退出聊天页再回来，没发出去的字还留在输入框里**
  - **背景**: 用户反馈「在聊天框打字然后退出这个聊天界面，他不会保留在聊天框里面的字」。
    在某一个会话里打了一半的话，返回会话列表（或切到别的角色）后重新进入，
    输入框是一片空白，打的字凭空消失，只能重写一遍。
  - **根因**: 输入框内容只有一个 `ChatUiState.inputText`，存在绑定在聊天页
    `backStackEntry` 上的 `ChatViewModel` 里（`NavGraph.kt` 里 `hiltViewModel()`
    写在 chat 路由的 composable 内部），返回时 ViewModel 被 `clear()`，
    这份内存状态随之蒸发；整个 chat 包此前没有任何持久化手段
    （`SavedStateHandle` / `rememberSaveable` / 草稿表全是 0 处，
    唯一相关的只有"发送失败回填"这种内存级补偿）。
    由此还带出两个隐患：`inputText` 是**全局单字段而不是按会话隔离**，
    切换会话时旧会话未发送的内容会跟着串到新会话；类型也只有一个 `String`，
    光标位置从未被建模。
  - **修复**:
    - 新增 `app/src/main/.../data/local/preferences/ChatDraftStore.kt`：独立 SP 文件
      `chat_input_drafts`，按会话 id 存一条草稿（`draft_<sessionId>` + 时间戳
      `ts_<sessionId>`），提供 `readDraft` / `writeDraft`（异步 apply）/
      `writeDraftSync`（同步 commit）/ `clearDraft`；写空串即删草稿，
      条数超过 100 时按最后编辑时间淘汰最旧的。不并进 `AppPreferences` 是因为
      草稿是随会话累积的临时数据，需要单独清理与淘汰。
    - `presentation/chat/ChatViewModel.kt` 新增三个方法：
      - `rotateInputDraftOnSessionChange()`：跟着 `sessionRepository.observeCurrentSession()`
        做草稿的「换主」与回填。会话从 A 切到 B 时，先把输入框里 A 没发的话写回 A，
        再把 B 的草稿读回输入框；进页（还没有旧归属）只在输入框为空时补位，
        不覆盖用户已经敲进去的内容。**换主与回填放在同一个协程里串行执行**，
        是为了不给自动保存流水线留下"把 A 的话写成 B 的草稿"的窗口。
        退出聊天页后重新进入走的是同一条链路 —— 那时是一个全新的 ViewModel，
        靠它把草稿读回来。
      - `persistInputDraftOngoing()` + `scheduleDraftPersist()`：停手 400ms 后异步落盘，
        避免每敲一个字触发一次 SharedPreferences 全量写。挂在 `uiState` 而不是
        `updateInputText` 上，因为输入框内容的来源不止一处（语音识别回填、
        发送失败回填、发送后清空），只有跟状态走才漏不掉 —— 其中"发送后清空"
        必须同步删草稿，否则下次进来会看到已经发出去的内容。
      - `flushInputDraft()`：把输入框最后的内容同步 commit，`ChatScreen` 的
        `DisposableEffect(onDispose)` 与 `ViewModel.onCleared()` 各兜一层，
        覆盖返回列表 / 手势退出 / 进程回收前等各种退页路径留下的 debounce 窗口。
    - `presentation/chat/ChatScreen.kt`：离开页面时调用 `flushInputDraft()`。
  - **验证**:

- **断句器误切数学区间：`[1, 3]` 被断成 `[1` / `3]` 两行，逗号消失**
  - **背景**: 用户在安卓端看到 AI 回复里的数学区间被硬生生切开：
    「在区间 [1, 3] 上的最小值」显示成「在区间 [1」+「3] 上的最小值」两段，
    逗号也没了。带逗号的数学表达式（区间、集合、坐标）每次都会中招。
  - **根因**: 断句器 `split_chat_message`（Python 与 Kotlin 两端同源）有条
    「显式空格分泡」规则：逗号/分号后跟空格视为用户主动分泡，**无条件断句**
    （不受逗号断句概率与长度阈值限制），断点标点被吃掉。模型写数学内容时
    按英文排版习惯输出 `[1, 3]`（逗号后带空格），正好命中这条规则。
    而括号配对栈（用于"括号内不断句"）只登记了 `（ ( " '`，
    **方括号 `[`、花括号 `{`、方头括号 `【` 不参与配对**，
    所以 `[1, 3]` 内部的逗号照样触发断句。Python 端实测复现：
    `split_for_display("...在区间 [1, 3] 上的...")` → `["...在区间 [1", "3] 上的..."]`。
  - **修复**: 把 `[`/`]`、`{`/`}`、`【`/`】` 加入断句主循环的括号配对栈
    （`core/utils/text_segmenter.py` 的 `closing_to_opening`/openers 判定，
    与安卓端 `ChatMessageSplitter.kt` 同步修改）。方括号/花括号内不再断句，
    「逗号+空格=主动分泡」对普通文本的既有行为保持不变（段尾逗号保留）。
    顶部「`[THINK_STORE: ...]` 整段直返」的特殊处理不受影响。
  - **验证**:
    - `tests/unit/test_text_segmenter.py` 新增
      `test_bracketed_math_interval_with_spaced_comma_not_split`：区间 `[1, 3]` /
      集合 `{1, 2, 3}` 整句保留，同时对照断言普通文本「写完作业， 早点睡」
      仍在显式空格处断句（防止修过头）。
    - `venv_core` 跑 Core CI 同款 pytest：断句模块 14 用例全绿，全量
      1241 passed；另有 2 个与本次无关的用例在全量跑时偶发失败
      （`test_storage_hotpath_optimizations` / `test_study_library`），单独重跑即绿，
      属既有环境性 flaky，非本次引入。
    - 安卓端 `TextSegmenterTest.kt` 新增 `方括号内逗号加空格不断句` 用例，
      **待编译验证**：按项目规则在 Android Studio 编译并跑该测试类回传结果。
  - **备注**: 两端规则常量对齐由 `tests/scripts/android_frontend/verify_text_segmenter_parity.py`
    校验，本次通过。未闭合的孤立 `[` 会压制其后断句（与未闭合 `(` 行为一致），可接受。

- **修「角色反复睡觉→被叫醒→又睡→催用户睡觉」的震荡循环（并补齐配置真正可改）**
  - **背景**: 用户反馈上一轮（09-21）的修复没生效，「还是老叫我睡觉」。用户补充
    自己确实是凌晨起来在正常聊天，但角色每 1~2 分钟就发一条"我先睡了"的告别。
    用户要求把睡眠判定阈值做成**真能改**的配置。
  - **根因（真正的）**: 与上一轮修的"BERT 起床信号被丢弃"是**两条不同链路**。
    真正的病根是角色作息引擎的自我震荡循环，日志实证：
    ```
    04:31:29  ReplyPolicy: 睡觉中，静默累积消息 (count=3, will_process_on_wake)
    04:31:29  ReplyPolicy: 不可打扰但被强制唤醒（prob=1.00），延迟 0.1s 回复
    04:31:29  RoleWakeCtx: DND 累积计数已重置（成功唤醒）
    04:31:30  角色 aveline 进入 SLEEPING（prev=fully_awake），已异步触发晚安主动消息
    04:31:31  角色 aveline 进入 WAKING_UP（prev=night_awake），已异步触发起床问候消息
    04:31:31  角色 aveline 进入 SLEEPING（prev=fully_awake），已异步触发晚安主动消息
    ```
    闭环：角色按作息表（`character_daily.yaml` 里 aveline `sleep_time=23:00` /
    `wake_time=07:00`）在凌晨本就处于睡眠窗口 → `sleep_manager.get_activity_override`
    返回 `sleeping`（DND）→ 用户发消息被 `reply_policy` 判"静默累积" →
    因为用户身份又按递增概率表强制唤醒回复 → 唤醒后 `reset_role_dnd_count`
    把计数清零 → 下一轮又判"在睡"。**每一轮"进入 SLEEPING"都触发一次
    `goodnight_proactive`**，其 prompt 模板（`TASK_GOODNIGHT_PROACTIVE_TEMPLATE`）
    硬塞"现在是 {tod} / 可靠状态表示你（角色本人）准备睡觉 / 必须表达角色自己
    准备去睡"，于是用户在正常聊天时被反复催睡。
    用户的真实作息（三星健康 + 聊天推断）在这条链路上**完全没被使用**：
    角色睡眠窗口只来自 `character_daily.yaml`；设备数据最新是 09-18（已过期 4 天），
    被 `DEVICE_SLEEP_FACT_MAX_AGE_HOURS=72` 的守卫正确丢弃，prompt 侧本就干净。
  - **根因（附带的 MDP 学习污染）**: MDP 把"用户回复"一律当 +1.0 奖励
    （`mdp.py` 注释：+1.0 用户回复 / -1.0 用户忽略），导致
    `late_night|sleep|replied::goodnight_proactive` 的 Q 值虚高到 **0.863**
    且已执行 **51 次**——凌晨每次回复都在强化"深夜发晚安=受欢迎"。
  - **根因（配置形同虚设，用户核心诉求）**: 上一轮往 `app.yaml` 加的 3 个配置项
    （`active_care_bert_wakeup_exit_threshold` / `active_care_daytime_exit_activity_seconds`
    / `study_mode.*`）**在运行时全部读不到**，永远走代码默认值——用户改 yaml 无效。
    原因是 `life_simulation` 是 pydantic 的 `LifeSimulationSettings`，只有**类里显式
    声明过的字段**才会被 `get_settings()` 加载；`extra="allow"` 只在构造时传参才生效，
    YAML 里的未声明键不会进 `model_extra`（实测为空）。
    另外 `study_mode_tool._study_cfg` 还拼错路径：用 `get_active_care_config(key)`
    得到 `life_simulation.study_mode_session_ttl_seconds`，而 yaml 里在
    `life_simulation.study_mode.*` 下，永远对不上。
  - **修复**:
    - `sleep_manager.get_activity_override`：`phase==SLEEPING` 时若用户正在跟该角色
      聊天，则不再覆盖成 `sleeping`（角色保持清醒陪聊）。新增
