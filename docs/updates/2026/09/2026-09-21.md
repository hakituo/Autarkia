- **修复安卓端同一轮多张表情包被折叠成"版本"、要点切换键才看得到**
  - **背景**: 用户反馈「角色表情包在安卓端连着发几个，也是点切换键才看得到，而不是连着
    几个竖着发出来」。QQ/微信 里角色连发 3 张表情包就是 3 条气泡竖着排下来，
    安卓端只显示第 1 张，右侧多出一个 `1/3` 版本切换键。
  - **根因**: 走 HTTP SSE 生成时，AI 正文气泡先以 `aiPlaceholder` 落库，随后每个
    `image_result` / `video_result` 事件都建成 `parentId = aiMessageId` 的消息。
    而消息树把「同一父节点 + 同为 AI/用户」的节点当作**互为版本**：
    `selectActiveMessageEntities` 每个节点只跟一个 `isActiveVariant` 的子节点走，
    `selectActiveConversationPath` 再把 `variantCount = siblings.size` 补上
    （见 `MessageTreePaths.kt` / `ChatRepositoryImpl.selectActiveConversationPath`）。
    于是同一轮的三张图变成三条"版本"，UI 只渲染其中一条并画出切换键。
  - **修复**: `presentation/chat/ChatSendController.kt` 的 `runAssistantGeneration`
    增加本轮媒体链尾 `mediaTailId`（初值 null 表示还没发过图）：
    第一张图挂在 `aiMessageId` 下（行为不变），之后每张图挂在**上一张图**下面，
    形成 `user -> aiText -> img1 -> img2 -> img3` 的链。链上每个节点的兄弟数都是 1，
    `variantCount = 1`，不再出现切换键，三张图各占一条气泡按顺序竖排。
    视频与图片共用同一条链（图文混发也保持顺序）。

      「同一轮多张表情包串成链时全部按顺序渲染」（路径含全部 3 张、`variantCount`
      均为 1）与反例「同一轮多张表情包都挂在正文下会被折叠成版本」（只出 1 张、
      `variantCount = 3`），把"媒体消息必须串链"这条不变量钉住。

  - **背景**: 用户同一条反馈的另一半——「角色表情包在安卓端是固定发到最后一个，

    图永远堆在整段回复的最后。用户明确要求走"方案①"：后端在标签位置就下发媒体事件，
    做真正的流式插空。

- **修复角色发图时偶发闪退：分段占位消息"先落库后上屏"撞出 LazyColumn 重复 key**
  - **背景**: 用户反馈「角色给我发表情包会导致 app 崩溃闪退」，且是**偶尔**崩；
    同一条反馈里表情包的"按标签位置分段"是正常的（"发确实是分段发的"）。
    服务端日志（会话 `web_role_ye`，用户 `mobile_user`）显示崩溃正好发生在
    `[media_tags] 推送图片` 那一刻，紧接着 WebSocket 以 `1006` 异常断开、
    2 秒后重连 —— 说明是客户端在收到媒体事件时挂掉，不是后端问题。
  - **根因**: 上一版新增的 `sealTextBubbleAndStartNext`（在媒体事件处给正文气泡封口，
    并在媒体下面新开一条空正文占位当链上的连接点）里，两条语句顺序写反了：
    ```kotlin
    chatRepository.insertMessage(nextPlaceholder)                      // 先落库
    withUiIfActive { uiState.update { messages + nextPlaceholder } }   // 后上屏
    ```
    而 UI 列表是"乐观上屏 + Room Flow 整体覆盖"两条路并存（见
    `ChatSessionObserver.observeMessages` 里的 `copy(messages = messages)`）。
    `insertMessage` 返回后 Room 的 Flow 随时可能发射，把 `messages` 整体替换成
    **已经包含这条占位**的活跃路径；若这次发射恰好挤在"落库"和"上屏"之间，
    紧接着的 `+ nextPlaceholder` 就把同一条消息加了第二次，
    `ChatMessageList` 的 `LazyColumn(key = { messages[it].id })` 撞上重复 key →
    `IllegalArgumentException: Key "..." was already used`，整个进程闪退。
    因为是竞态，所以表现为"偶尔崩"；又只有媒体事件才会走封口逻辑，
    所以只在有表情包/图片的那一轮出现。
    同类代码里这是唯一的顺序反例：用户消息与图片/视频消息都是"先上屏、后落库"，
    且 `ChatSendController` 里本来就有注释写明"Room 只在事务提交后通知，
    下一次回流必然包含这条消息，不会重复也不会丢"。
  - **修复**: 占位消息改成与图片/视频一致的**先上屏、后落库**；同时把这次 append 做成
    幂等（`state.messages.filterNot { it.id == nextPlaceholder.id } + nextPlaceholder`），
    即使别处再补一次也不会撞 key。
  - **顺带修掉一个上一版引入的回归（连发多张表情包只剩第一张）**:
    上一版用 `mediaTailId`（"媒体链尾"）决定下一张图挂在哪里，但封口逻辑**总会**在媒体
    下面新开一条空占位，于是"下一张图挂上一张图"的规则让第二张图与那条空占位同父、
    同为 AI、互为版本；`selectActiveMessageEntities` 每层只跟一个激活子节点，
    空占位时间更早被选中，第二张图连同它下面整条子树都从活跃路径上消失。
    修复方式是直接删掉 `mediaTailId`，媒体一律挂在**当前正文气泡**（`textMessageId`）下：
    封口时新开的气泡自然成为下一次的挂载点，链路天然是
    `正文1 -> 图1 -> 空占位 -> 图2 -> 空占位 -> 图3 -> 正文2`，每一环兄弟数都是 1。
  - **验证**:
    - `MessageTreePathTest` 新增两条用例：「连发多张表情包时每张图之间夹着空占位仍按顺序
      全部渲染」（钉住真实链路形状：三张图都在活跃路径上、都没有版本切换键）与反例
      「第二张图挂回第一张图下会被空占位挤出活跃路径」（钉住 `mediaTailId` 写法的后果）。
    - **待编译验证**：按项目规则安卓端不在沙箱跑 gradle，需在 Android Studio 编译并跑
      `MessageTreePathTest` 回传结果。

- **给后台生成协程补异常兜底：回复生成失败不再赔上整个进程**
  - **背景**: 上一条崩溃能"闪退"而不是"这一轮报错"，根因之外还有一层结构性原因：
    `ChatSendController.backgroundGenerationScope` 用的是
    `CoroutineScope(SupervisorJob() + Dispatchers.IO)`。`SupervisorJob` 只保证
    "一条生成失败不取消其它并发生成"，它**不负责兜住异常** —— `launch` 里抛出的未捕获异常
    会一路交到线程默认异常处理器，被 `CrashHandler` 记档后**直接杀掉进程**。
    而 `runAssistantGeneration` 只有 `try/finally`、没有 `catch`，于是流式过程中任何
    未预期异常都会升级成整机闪退。
  - **修复**:
    1. `backgroundGenerationScope` 加上 `CoroutineExceptionHandler`：作为最后一道网，
       任何漏网异常只记日志、不再杀进程。
    2. `runAssistantGeneration` 的 `try/finally` 补上 `catch`：
       - `CancellationException` **原样上抛**（用户离开页面 / 后端 cancel 上一轮属于正常取消，
         吞掉取消信号会让上层误以为这一轮正常跑完）；
       - 其余异常记 `Log.e` + 置用户可见的 `error` + 关掉打字指示器，
         避免界面永久卡在"正在输入"。
  - **验证**: 逻辑改动，无对应自动化断言（异常注入需要 Instrumented 测试环境）。
    **待编译验证**：需在 Android Studio 编译并确认无警告/报错。

    - `check_network_ready()` 的 fallback 从 `socket.create_connection(...)` 换成 `tls_probe()`。

- **修「乱进学习模式」与「起床了仍被当晚安模式」两个体感问题（阈值全部可配）**
  - **背景**: 用户反馈两个问题。
    (1) 随便闲聊（聊安卓开发/软硬件）时角色自称「进入学习模式」，还编出用户从没提过的
        「物理 / 费米能级」来追问；
    (2) 一直催睡觉——用户 15:55 说了「我准备睡了」是真去睡了，22 点起来说了「我醒了」，
        系统却**没有退出**晚安模式，整晚一直当他是睡着的。
    用户明确要求：这两个问题的判定阈值都要**可修改**，不能写死。
  - **根因（问题一）**: `enter_study_mode` 是 LLM 自主调用的原生工具，
    `core/tools/study_mode_tool.py` 的工具描述写得过宽（「用户开始学习、请教知识、
    讨论学术话题时调用」），普通闲聊里出现一两个专业名词就会被误判成学习；
    而 `_study_sessions` 是纯内存 `Dict`，**没有任何过期机制**，一旦进入就永久锁死，
    LLM 自己也退不出来。
    日志实证：
    ```
    [23:05:42] PromptData: ... Mode=study ...
    [23:05:47] [Native Tool] Executing: enter_study_mode
    [23:05:47] [Tools.StudyMode] 用户 web_role_aveline 进入学习模式 subject=物理 topic=费米能级
    ```
  - **根因（问题二，真正的 bug）**: 15:55 的晚安判定是**对的**（用户确实说了「我准备睡了」），
    坏在退出路径。BERT 意图检测**已经正确识别**了起床：
    ```
    [22:24:20] [MODE_STATE] 忽略缺少明确起床陈述的 BERT WAKEUP_NOW: conf=0.80 text=才醒
    [22:39:22] [MODE_STATE] 忽略缺少明确起床陈述的 BERT WAKEUP_NOW: conf=0.60 text=...我睡觉的时候也被她吵醒了...
    Active Care: 仍在晚安模式，无法退出 (goodmorning=False, awake=False, ...)
    ```
    但 `core/services/active_care/state/mode_state.py` 里有一段无条件丢弃：
    ```python
    if state_event == "WAKEUP_NOW":
        logger.info("忽略缺少明确起床陈述的 BERT WAKEUP_NOW: ...")
        return {"action": "none"}
    ```
    于是退出闸门（`sleep_session_manager.py`）永远收不到信号，从 16:51 到 22:24 每 5 分钟
    空转一次。
  - **修复（问题一，`core/tools/study_mode_tool.py`）**:
    - 工具描述重写，**显式排除**：普通闲聊/吐槽/日常分享；随口提到专业名词；
      用户在教你；单点事实问题。并要求 `subject/topic 必须来自用户原话`。

      `idle_turn_count` / `exit_reason`；新增 `_exit_with_reason()` 与
      `tick_study_session(user_id, has_learning_signal)`，实现**四路自动退出**：
      累计轮数超限、会话超时（TTL）、连续无学习信号轮数超限、空闲时长超限。
