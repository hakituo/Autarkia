## 2026-05-28 修复双QQ人设优先级：adapter自身配置为主，不是fallback

### 问题
- 双QQ模式下，Ling的QQ仍然使用Aveline的人设和模型
- 根本原因：之前的设计把override作为主要来源，adapter自身配置只是fallback
- 当override为空或错误时，fallback会用到错误的值（如DEFAULT_PROFILE_FILENAME指向Aveline）
- `get_session_prefs`中还有对无role_id的override key（`10001`）的危险fallback

### 修复
- **`get_session_prefs`**：双QQ模式下，`profile_filename`和`reference_audio`以adapter自身配置（来自`dual_qq_config.json`）为主，override只用于模型等可变设置
- **`get_session_prefs`**：移除对无role_id的override key的fallback，双QQ模式只用`{qq_user_id}__{role_id}`，单QQ模式只用`qq_user_id`
- **`_sync_config_from_backend`**：双QQ模式下始终使用adapter自身配置的persona和reference_audio写入override，不从后端API获取
- **`config.json`**：删除残留的无role_id的`10001` key，避免危险fallback

### 设计原则
- adapter自身配置（`dual_qq_config.json`中的`profile_filename`和`default_reference_audio`）是源头，不是fallback
- override是持久化机制，不是配置来源
- 双QQ模式下，每个adapter的人设和声音由其自身配置决定，不可能出现错误

### 修改文件
- `clients/bots/handlers/config.py` - get_session_prefs 优先级重构
- `clients/bots/qq_adapter_main.py` - _sync_config_from_backend 逻辑优化
- `clients/bots/config.json` - 清理残留key

## 2026-05-28 修复 profile_filename 在 WebSocket 标准化时被丢弃（根因）

### 问题
- 双QQ模式下，Ling的QQ始终使用Aveline的人设，即使conversation_id正确包含了`ling_qq_master`
- 后端日志显示 `profile_filename=''`，说明 profile_filename 没有传到后端

### 根因
- `handle_text_message`（handlers.py 第459-466行）在标准化 `text_input` 类型消息时，只保留了6个字段
- `profile_filename` 和 `peer_role_context` 被丢弃
- QQAdapter 的 `send_text` 发送的 payload type 是 `text_input`，所以一定会经过这个标准化路径
- 这就是为什么 conversation_id 正确（在标准化前构建）但 profile_filename 为空（标准化后丢失）

### 修复
- 在 `handle_text_message` 的标准化结果中保留 `profile_filename` 和 `peer_role_context` 字段

### 修改文件
- `core/interfaces/websocket/adapters/handlers.py` - handle_text_message 保留 profile_filename 和 peer_role_context

## 2026-05-28 修复 Active Care 双QQ模式下Ling从不发消息（scope隔离）

### 问题
- Active Care只有Aveline发消息，Ling从不发
- 根因1：`_execute_decision_flow`在读取proactive_state之前没有设置正确的scope，所有persona共享同一个proactive_state.json

- **storage.py**：添加`resolve_scope_from_profile_filename`方法，直接从profile_filename解析scope
- **proactive_checker.py**：`_execute_decision_flow`在读取state之前，先根据profile_filename设置正确的scope
- **proactive_checker.py**：双QQ模式下，用profile_filename构建正确的primary_cid，不依赖全局resolve

### 修改文件
- `core/services/active_care/storage.py` - 新增 resolve_scope_from_profile_filename
- `core/services/active_care/proactive_checker.py` - _execute_decision_flow scope隔离

## 2026-05-28 修复双角色私聊persona错乱（根本原因：非主人私聊强制用PUBLIC_PERSONA_FILE）

### 问题

### 修复

- 删除了错误的聊天记录和短期记忆文件

## 2026-05-28 双角色私聊session_id从private_改为peer_，修复persona错乱

### 问题
双角色私聊时 session_id 用 `private_{对方QQ号}`，无法区分"跟主人聊天"和"跟对方bot聊天"，导致：
1. 聊天记录落盘到主人的数据目录
2. Ling的adapter收到Aveline消息后，用Aveline的人设回复（两个Aveline在聊天）
3. conversation_labels 无法正确识别双角色私聊

### 修复
- **session_id格式**：双角色私聊用 `peer_{对方QQ号}` 替代 `private_{对方QQ号}`
- **send_to_napcat**：支持 `peer_` 前缀，和 `private_` 一样发私聊消息
- **parse_session_user_id**：支持 `peer_` 前缀解析
- **conversation_labels.py**：新增 `is_peer_chat` 识别，`ling_qq` persona 的 storage_scope 正确映射到 `ling`，双角色私聊 lane_name 为"双角色私聊"
- **data_paths.py**：`resolve_data_scope_from_conversation_id` 精确匹配 `__persona__ling_qq` 和 `__persona__aveline_qq`，不再用模糊的 `_ling` 匹配
- **config.py**：`get_session_prefs()` 中新增 `is_peer_bot` 判断，对方bot使用adapter自身persona而非PUBLIC_PERSONA_FILE
- **dual_qq_active_dialogue.py**：发起互聊时用 `peer_{对方QQ号}`

### 删除的错误数据
- aveline_data 下 private_123456789 和 private_123456789 的聊天记录和短期记忆
- ling_data 下错误的 aveline_qq_master 记录
