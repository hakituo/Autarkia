## 2026-05-08
- **🐛 修复 Memory 异步保存 WinError 2（系统找不到指定的文件）**：
  - 根因1：`lifecycle_ops.py` 的 `safe_save_all` 中 `os.path.exists()` + `os.remove()` 存在 TOCTOU 竞态条件——异步保存线程和自动保存线程并发执行时，一个线程检查到文件存在后另一个线程先删除了该文件，导致 `os.remove` 抛出 `FileNotFoundError`（WinError 2）
  - 根因2：`persistence.py` 的 `safe_json_dump` 使用固定 `.tmp` 后缀作为临时文件名，并发写入同一目标文件时，一个线程的 `.tmp` 文件可能被另一个线程的 `os.replace` 移走，导致源文件不存在
  - 修复1：将所有 `os.path.exists()` + `os.remove()` 模式替换为 `try: os.remove() except FileNotFoundError: pass`，消除竞态窗口
  - 修复2：临时文件名改为 `.tmp_{线程ID}_{进程ID}` 格式，确保并发写入时各线程使用独立的临时文件
  - 涉及文件：`memory/core/lifecycle_ops.py`、`memory/core/persistence.py`、`memory/core/io_ops.py`
- **🐛 修复 Active Care 白天(10-18点) reduced_mode 不自动退出导致整天不发主动消息**：
  - Bug4: `proactive_checker.py`: probable_sleep/sleep_hint 模式到白天(10-18点)不自动退出，只有检测到"早安"/"醒了"等关键词或14小时超时才退出 → 用户白天正常聊天但不触发清醒关键词，reduced_mode 一直卡着
  - Bug5: `proactive_checker.py`: goodnight 模式白天也不退出，同样需要清醒关键词或14小时超时
  - Bug6: `decision_executor.py`: `_is_override_allowed` 对 goodnight 模式白天也完全阻止覆盖 → 即使长沉默也无法强制发送
  - 修复：probable_sleep/sleep_hint 在白天(10-18点)无条件自动退出；goodnight 在白天且有用户信号时自动退出；goodnight 白天允许长沉默覆盖（与 probable_sleep 同等待遇）
  - 验证脚本：`tests/diagnostics/active_care_review/verify_active_care_probe_fix.py`（24项全通过）
- **🐛 修复 Active Care 长沉默阈值过低导致忽略用户已知状态**：
  - 根因：`LONG_SILENCE_THRESHOLD_SECONDS` 原为600s（10分钟），用户聊完天后15分钟即触发"长沉默"模式。该模式下 `_build_proactive_trigger_input` 指令为"不要复读或追问用户最后一条消息"，LLM理解为"忽略用户最近说的话"，导致对已知事实（如用户已告知起床时间）假装不知道并重新追问
  - 修复1：将 `LONG_SILENCE_THRESHOLD_SECONDS` 从600s提高到1800s（30分钟），10-30分钟内保持延续模式，LLM自然顺接最近对话
  - 修复2：将proactive trigger指令从"不要复读或追问用户最后一条消息"改为"不要复读用户最后一条消息，但用户已告知的事实必须尊重"，去掉"追问"这个过度约束
- **🐛 修复 retry 逻辑未处理 tool_calls 返回值，导致用户收到空回复**：
  - 根因：当 LLM 多轮 tool call 后只返回思考内容无可见文本时，触发 retry 逻辑。retry 使用非流式 `chat()` 调用，但 DeepSeek v4 仍通过 DSML 格式输出 tool call，DSML 兜底解析将 content 清空提取 tool_calls，retry 代码只取 `response`/`content` 字段，完全忽略 `tool_calls`，导致 `retry_text` 为空，用户收到空回复
  - 修复1：retry 返回值新增 `tool_calls` 处理分支——执行工具、追加结果到 messages、再调用一次 LLM 生成文本回复
  - 修复2：retry 生成的文本逐字 yield 给前端，保证打字效果
  - 修复3：二次调用仍返回 tool_calls 时记录 warning 日志，不再无限重试
- **🐛 修复 `get_daily_summary` 当天无作息记录时不回查历史，导致 LLM 不知道用户作息规律**：
  - 根因：`get_daily_summary` 只查当天的 `daily_record.json`，如果当天还没记录 wakeup/sleep，LLM 就不知道用户作息。重启后当天记录可能还没写入，LLM 调 `search_memory` 也搜不到（`daily` category 权重低、可能被预算截断）
  - 修复：`DailyActivityManager` 新增 `_infer_schedule_pattern()` 方法，从最近 7 天的 `daily_record.json` 中提取作息规律。当当天无作息记录时，自动追加"近期作息规律"到 summary 中
- **🐛 修复 Active Care 无法感知尚未落盘的用户消息，导致误判用户入睡**：
  - 根因：用户消息要等 LLM 生成完回复后才保存到记忆管理器历史，但 Active Care 多处代码只从历史记录读取，不检查 `_recent_user_message_cache` 缓存
  - 现象1：用户发消息后，Active Care 的 `_process_user_response` 看到历史中最后一条消息是旧的（>300s），跳过处理，不调用 `_reset_interaction_state`，`probable_sleep` 模式不会被清除
  - 现象2：`get_user_signal_and_intent` 返回的 `inferred_ts` 是旧消息的时间戳，导致 `latest_user_signal_ts` 也是旧的，`_try_infer_probable_sleep` 错误推断用户长时间沉默
  - 现象3：`proactive_checker.py` 的 `ctx.full_history` 缺少最新用户消息，影响 `last_interaction` 时间戳推断和对话上下文分析
  - 修复1：`service.py:_process_user_response()` 新增缓存检查逻辑，当缓存消息比历史消息更新时使用缓存消息
  - 修复2：`decision_executor.py:get_user_signal_and_intent()` 新增缓存检查逻辑，当缓存消息比历史消息更新时使用缓存消息的 `content` 和 `timestamp`
  - 修复3：`proactive_checker.py:_execute_decision_flow()` 在加载 `ctx.full_history` 后用缓存补全尚未落盘的最新用户消息
