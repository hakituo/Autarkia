## 2026-05-03
- **🐛 修复 `continuation_anchor` 优先选择 proactive 消息，忽略更新的 normal chat 消息**：
  - `_build_model_user_input_for_active_care` 中 `continuation_anchor` 的 `or` 链把 proactive 放在前面，导致 even 有更新的 normal chat 消息时仍用旧的 proactive 做锚点
  - 例：08:46 normal chat 说"睡醒再说"，08:51 Active Care 的 anchor 却用 08:45 proactive "喂，再装死我真的不管了" → LLM 继续催起床
  - 修复：改为 `last_assistant_message or last_proactive_assistant_message`，最近消息优先
- **🐛 修复 `elapsed_seconds` 被 Assistant 消息时间覆盖导致 Active Care 错误判定"长静默"**：
  - `_build_trigger_context` 中 `elapsed_seconds` 的初始值（用户静默时间）被 Assistant 最近消息时间覆盖，导致 Assistant 刚回复完后 15 分钟就触发"长静默"模式
  - 长静默模式下 LLM 被指令要求忽略对话历史、基于时间开启新话题，导致 08:05 说"去睡觉"、08:20 说"起床"的矛盾
  - 修复：新增 `user_elapsed_seconds` 单独追踪用户静默时间，`is_long_silence` 判断改用此值
- **🐛 修复 QQ Adapter WebSocket 路由 user_id 与 persona conversation_id 不匹配**：
  - QQ Adapter 注册 WebSocket 连接时使用原始 `session_id`（如 `private_10001`），但 Active Care 使用带 `__persona__` 后缀的 conversation_id 做 WebSocket 路由，导致 `broadcast()` 找不到连接
  - 修复 `dispatch_proactive_message()`：QQ 路由时剥离 `__persona__*` 后缀计算 `broadcast_user_id`；payload 中的 `conversation_id` 保持 persona ID 不变（QQ Adapter handler 已有 base CID 匹配）；`append_proactive_message` 仍使用 persona ID 存储
  - `is_user_online()` 同步修复
- **🐛 修复 "Thinking Process:" 解析正则过于严格，无法识别 Qwen 输出格式**：
  - Qwen3.5-27B 输出的推理文本为裸 `Thinking Process:` 格式（无 `> ` 前缀、无 `**` 加粗），原有正则只匹配 `> **Thinking Process:**`，导致推理文本无法被剥离
  - 修复 `decision.py:_extract_json_block()` 和 `postprocessor.py:strip_reasoning_segments()` 的正则：使前缀/加粗标记可选，同时支持中文 "思考过程：" 格式
  - 推理文本残留可能导致 JSON 解析失败，Checker 错误判定 `should_send=False`
- **🐛 修复 Active Care 消息类型不匹配导致QQ端收不到主动消息**：
  - 根因：`dispatch_proactive_message()` 的 payload 使用 `"type": "proactive"`，但 QQ Adapter 只处理 `msg_type == "proactive_message"`，消息被静默丢弃
  - 修复：将 payload type 从 `"proactive"` 改为 `"proactive_message"`，添加 `"is_proactive": True` 标志
  - 修复 QQ Adapter `proactive_message` handler 中 `message_type` 取值错误：从 `data.get("subtype")` 改为 `data.get("message_type")`，否则语音类型判断永远不生效
  - 新增 `WebSocketManager.is_user_online()` 方法，改进日志区分"实时送达"和"存入离线队列"
- **🐛 修复 DeepSeek V4 DSML token 泄漏问题**：
  - DeepSeek V4 API 有时不解析内部 `<｜｜DSML｜｜>` 工具调用 token，导致原始 DSML 文本泄漏到 `content` 字段
  - 新增 `dsml_parser.py`：支持 V4（双全角竖线）、V3.2（单全角竖线）、Plain 三种 DSML 格式的解析
  - 非流式路径：在 `_parse_non_stream_response()` 中添加 DSML 兜底解析，自动将泄漏的 DSML token 转为结构化 `tool_calls`
  - 流式路径：在 `OpenAIClient._process_stream_chunk()` 中拦截 DSML token，缓冲完整块后解析为 `tool_calls`，防止原始 DSML 文本流到前端
  - streaming.py 中添加 DSML 残留清理（安全网），确保前端不会看到任何 DSML token
  - 测试脚本：`tests/diagnostics/test_dsml_parser.py`

- **⚡ 优化QQ消息发送延迟**：
  - 降低最小延迟：`min_seconds` 从 1.6秒 → 0.5秒，让短句发送更快
  - 增加每字延迟：`per_char_seconds` 从 0.18秒 → 0.25秒，让长句延迟更明显
  - 新的延迟计算：`delay = max(0.5秒, 字符数 × 0.25秒)`
  - 示例对比：

    - "我忘了……"（5字）：旧 1.6秒 → 新 1.25秒
    - "这是一个中等长度的句子"（11字）：旧 1.98秒 → 新 2.75秒
    - 30字长句：旧 5.4秒 → 新 7.5秒（达上限）
