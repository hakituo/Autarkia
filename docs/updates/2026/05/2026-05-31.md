## 2026-05-31 修复 Active Care 消息从错误的 QQ adapter 发送（dual QQ 模式路由 bug）

### 问题
Active Care 发出的消息风格像Ling而不是 Aveline。在 dual QQ 模式下，proactive message 的路由逻辑有 bug，导致消息可能从错误的 adapter 发送。

### 根因
`qq_adapter_session.py` 中 proactive message 的路由逻辑（line 1032-1035）只检查 `base_cid == self.session_id`，但在 dual QQ 模式下，Aveline 和 Wang Ling 的 adapter 共享同一个 `base_cid`（如 `private_10001`）。因此当 active care 为 Aveline 发送消息时，Wang Ling 的 adapter 也会匹配并尝试发送消息。

虽然 `_is_duplicate_proactive_global` 去重机制可以防止重复发送，但存在竞态条件：如果 Wang Ling 的 adapter 先处理消息，消息会从 Wang Ling 的 QQ 账号发出，即使内容是为 Aveline 生成的。

### 修复
- **qq_adapter_session.py**：修复 proactive message 路由逻辑，当 `target_id` 包含 `__persona__` 时，检查 persona 是否匹配当前 adapter 的 `profile_filename`。使用 `build_persona_conversation_id` 构建期望的 conversation_id 进行精确匹配。

### 修改文件
- `clients/bots/qq_adapter_session.py` — 修复 proactive message 路由逻辑

## 2026-05-31 修复 Active Care 在 dual QQ 模式下看不到聊天上下文

### 问题
Active Care 发出的消息"看得什么类型的 说来听听"、"中午吃了吗还是刚醒"完全无视了刚结束的对话上下文（用户在聊外卖和代码）。跟看不到上下文一样。

### 根因
`context.py` 的 `get_latest_history` 使用 `get_candidate_conversation_ids()` 获取候选对话 ID，但该函数使用全局 PersonaManager 的 persona token 来过滤候选。在 dual QQ 模式下，全局 PersonaManager 的当前 persona 可能与正在处理的 persona 不一致，导致历史记录从错误的对话中获取。

例如：正在为 Aveline 处理主动关怀，但全局 PersonaManager 的当前 persona 是 Wang Ling，导致历史记录从 Wang Ling 的对话中获取，而不是 Aveline 的对话。

### 修复
- **context.py**：
  - `get_candidate_conversation_ids` 新增 `profile_filename` 参数，优先使用传入的 persona 进行过滤，回退到全局 PersonaManager
  - `get_latest_history` 新增 `profile_filename` 参数，传递给 `get_candidate_conversation_ids`
- **proactive_checker.py**：调用 `get_latest_history` 和 `get_user_signal_and_intent` 时传递 `profile_filename`
- **decision_executor.py**：`get_user_signal_and_intent` 新增 `profile_filename` 参数，fallback 调用 `get_latest_history` 时传递

### 修改文件
- `core/services/active_care/context.py` — 新增 profile_filename 参数支持
- `core/services/active_care/proactive_checker.py` — 传递 profile_filename
- `core/services/active_care/decision_executor.py` — 传递 profile_filename

## 2026-05-31 后处理剥离模型输出时间戳 + 修复时间戳正则bug

### 问题
1. **模型输出时间戳**：模型模仿历史消息中的时间戳格式输出时间戳（如 `[23:10] 好好好，不带了不带了`），发给用户时仍带时间戳
2. **原有正则只匹配行首**：streaming.py / handler.py / qq_adapter_session.py 中的时间戳剥离正则都用 `^` 锚点，只能匹配回复开头的时间戳，无法匹配中间出现的
3. **原有正则格式bug（两重）**：
   - 正则 `\d{2,4}-\d{2}-\d{2}` 期望两个 `-`（如 `[2025-05-22 01:45]`），但实际时间戳格式 `[05-22 01:45]` 只有一个 `-`
   - 正则要求日期后有空格，但模型输出的 `[23:10]` 格式没有日期部分也没有空格
   - 导致 `[MM-DD HH:MM]` 和 `[HH:MM]` 两种格式的时间戳从未被正确剥离

### 修复
- **正则重新设计**：`\[(?:\d{2,4}(?:-\d{2}){1,2}\s+)?\d{2}:\d{2}(?::\d{2})?(?:\s*\([^)]+\))?\]\s*`
  - 日期部分 `(?:\d{2,4}(?:-\d{2}){1,2}\s+)?` 整体可选，支持 `[HH:MM]`、`[MM-DD HH:MM]`、`[YYYY-MM-DD HH:MM]` 三种格式
- **全局匹配**：移除 `^` 锚点，可剥离回复中间出现的时间戳
- **共享函数**：在 `qq_adapter_utils.py` 新增 `strip_ai_timestamp()` 函数
- **四层防护**：streaming.py（后处理+流式前缀）、handler.py（后处理）、qq_adapter_session.py（发送前）、qq_adapter_transport.py（兜底）
- **历史记录去重**：剥离在保存历史记录之前执行，确保模型输出的时间戳不会进入历史记录和上下文

- `clients/bots/qq_adapter_utils.py` — 新增 `strip_ai_timestamp()` 共享函数
- `clients/bots/qq_adapter_session.py` — 使用共享函数替换原有行首匹配
- `clients/bots/qq_adapter_transport.py` — 新增兜底剥离
